Cross-cutting themes you keep demonstrating

What shows up in project after project

  • LLM output is untrusted input. Every AI project validates, retries, or gates the model's output — you never assume it's well-formed.
  • Human-in-the-loop by design. Draft/approve gates, quality thresholds, verdict bands — you don't let models act unsupervised.
  • Provider-swappable. Config-driven LLM choice (Gemini ↔ Ollama ↔ Claude) recurs — you decouple from any one vendor.

Engineering habits

  • TDD & test isolation (ContentPilot grew 39→98 tests; you caught tests polluting real data files).
  • Explainability over black-box (log-normalized virality score, statistical significance, tiered evaluation you can narrate).
  • Cost/latency awareness (cheap checks before expensive ones; background threads so UIs never block).

EMS 2.0 — AI Employee Management System

Natural-language CRUD over resumes, fully on-premise

AIFull-stack
FastAPI · PostgreSQL · MongoDB GridFS · FAISS · Ollama (qwen2.5:7b) · sentence-transformers

Upload a resume PDF/image → a local LLM extracts structured fields → stored in Postgres, indexed in FAISS → then you just chat: "find a DevOps engineer with Kubernetes experience", "update John's email". Runs entirely on a 6GB GPU, no data leaves the machine.

What you learned

  • Polyglot persistence — using three stores because each is best at one job (relational writes, binary blobs, vector search) instead of forcing one DB to do all.
  • RAG fundamentals: retrieval gates generation so the model answers only from real records.
  • Deterministic LLM calls: temperature=0, fixed seed, tuned context window for reproducible extraction.

Approach you took

  • Four-strategy JSON parse chain (direct → regex extract → regex cleanup → key-value fallback) + Pydantic validation, retry with stricter prompt if a required field is missing.
  • Resume scoring gate (threshold 40/100) — reject garbage before spending an LLM call.
  • Explicit threading.Thread(daemon=True) with flat-file job status the frontend polls.

Alternatives that exist

  • Structured-output APIs (OpenAI/Gemini JSON mode, function-calling, or Outlines/Instructor grammar-constrained decoding) would remove most of the parse chain — but aren't available for arbitrary local Ollama models, which is why you built the chain.
  • One database (Postgres with pgvector + bytea) instead of three — simpler ops, loses FAISS's raw ANN speed. A fair interview debate.
  • Task queue (Celery/RQ/Arq) instead of raw threads — more robust for scale, heavier to run locally.

Bug classes handled

  • Malformed LLM JSON, markdown-fenced output, dropped fields (the core reliability problem).
  • Input chaos: all-caps, emoji, unicode names, punctuation walls (documented stress suite).
  • Async timing bugs from BackgroundTasks + blocking calls → switched to explicit threads.

LLM Evaluation Framework

An automated quality gate for LLM apps

AIInfra
FastAPI · Celery · Redis · PostgreSQL · Streamlit · Plotly · Docker Compose

Submit a prompt/response via API → four independent evaluators run (LLM-judge, hallucination, RAG faithfulness, consistency) → results to Postgres, Slack alert on failure, live dashboard. Catches "model provider drift" — silent quality drops when a vendor updates a model with no changelog.

What you learned

  • Async job architecture: API returns 201 immediately, work happens on a Celery worker — the caller never waits.
  • The difference between "is this true?" and "did the model stay within retrieved context?" (RAG faithfulness vs correctness).
  • Multi-service orchestration with Docker Compose (5 services).

Approach you took

  • Each evaluator is independent with its own pass threshold — composable, individually testable.
  • Broker/worker split (Redis + Celery) so evaluation scales horizontally.
  • Dashboard polls rather than holding connections — simple and robust.

Alternatives that exist

  • Off-the-shelf: promptfoo, Braintrust, LangSmith, Ragas, DeepEval already do LLM eval. Your edge in interview: you built it and understand the internals, not that it beats them.
  • Queue choice: Arq or Dramatiq (async-native) vs Celery (mature, sync-oriented). RQ for simpler needs.
  • Streaming eval (Kafka) if volume were high — overkill here, worth naming.

Bug classes handled

  • Non-determinism in scoring → averaging multiple runs to separate signal from variance.
  • Judge cost/latency → thresholds and ordering so expensive checks are gated.

Bias & Fairness Auditor

Counterfactual fairness testing with statistical rigor

AI
FastAPI · Claude · VADER · DistilBERT · sentence-transformers · SciPy · fpdf2 · Streamlit

Run a prompt hundreds of times changing only the demographic signal (name, age, religion), measure whether tone/content/quality differ, produce a 0–100 bias score with a four-band verdict, remediation suggestions, and a PDF report structured for EU AI Act Article 13.

What you learned

  • Counterfactual fairness: hold everything constant, vary one signal, attribute the difference.
  • Statistical significance — a single run can't separate bias from random variance; you need N runs and a test.
  • Layered analysis: cheap signals first (word count, VADER), ML second (DistilBERT, embeddings), LLM-judge last (blind, demographics stripped).

Approach you took

  • Four independent analysis pipelines (sentiment, semantic, structural, LLM-judge) feeding one composite score.
  • Async execution with a semaphore cap to respect rate limits.
  • Regulatory output as a first-class feature (Article 13 docs), not an afterthought.

Alternatives that exist

  • Fairness toolkits: IBM AIF360, Microsoft Fairlearn, Google's What-If Tool — built for tabular ML, not free-text LLM output, which is the gap you fill.
  • Sentiment: VADER (lexicon, fast) vs a fine-tuned transformer (accurate, slow) — you used both in a two-layer design.

Bug classes handled

  • Statistical false positives — mitigated by significance testing rather than eyeballing means.
  • Judge contamination — demographics stripped before the LLM judge sees pairs (blind comparison).

Prompt Regression Suite

"pytest for prompts" — a CI gate for prompt quality

AIInfra
asyncio · Pydantic v2 · GitHub Actions · Anthropic/OpenAI/Ollama · Streamlit

Each prompt gets a behavioral test suite in a version-controlled YAML. Every PR touching a prompt runs its tests in CI; if quality drops below a stored baseline, the merge is blocked before the regression reaches users.

What you learned

  • Treating prompts as first-class software artifacts with version-controlled tests.
  • Reverse-index design: map changed files → affected tests, so a PR touching 3 of 80 prompts runs ~12 tests, not 80.
  • Deployment-gate thinking — blocking a merge, not just reporting.

Approach you took

  • Tiered assertion engine: rule checks (free) → semantic similarity (local) → LLM judge (paid, last). Fail-fast halves API cost.
  • asyncio.Semaphore to cap concurrent LLM calls without serializing.
  • Each case runs 3× and averages — one sample at temperature 0.7 is noise.

Alternatives that exist

  • promptfoo does much of this off the shelf; your version proves you understand the mechanism.
  • Snapshot testing (exact-match golden files) — brittle for stochastic output, which is why you scored semantically instead.

Bug classes handled

  • Silent prompt regressions that green unit tests miss — the whole reason the project exists.
  • Cost blow-ups from calling the judge on everything — gated by tier ordering.

ContentPilot 1.0 / 2.0 — Autonomous content + viral-prompt trend engine

Discover → generate → draft → approve → git-publish, on a schedule

AIFull-stack
Typer · FastAPI · Jinja2 · APScheduler · GitPython · Pydantic · Gemini / Ollama · pytest

1.0 is an agent pipeline that finds trending topics, generates posts + images, and pushes to a static-site git repo — with a dashboard, scheduler, and a draft/approve gate. 2.0 adds a trend-intelligence layer: pull viral prompts from Civitai + prompts.chat, score them with an explainable virality metric, and use an LLM to extract why each prompt works.

What you learned

  • Agent-pipeline design: one Orchestrator.run() reachable from CLI, dashboard button, or scheduler — one code path, three triggers.
  • Per-source failure isolation — one dead API marks a run "partial", doesn't kill it.
  • Explainable scoring: log-normalized-per-source virality, defensible in one sentence.
  • TDD at scale + test isolation (grew to 98 tests; caught tests writing into real data files).

Approach you took

  • Draft-by-default: automated runs stage to a local drafts/ folder; nothing goes live without human approval in the dashboard.
  • Pathspec-scoped git commits (git commit -- <path>) so a run never sweeps unrelated staged work.
  • In-process APScheduler inside the dashboard = one process is the whole control plane; cron documented as the headless alternative.

Alternatives that exist

  • Agent frameworks (LangChain, LangGraph, CrewAI) instead of a hand-rolled orchestrator — more features, more magic, harder to reason about. You chose legibility.
  • Scheduling: in-process APScheduler vs system cron vs Celery-beat vs a cloud scheduler — you shipped the first, documented the second.
  • Publish target: git-based vs a headless CMS API. Git gives you free version history.

Bug classes handled (real, specific — great interview stories)

  • Git index sweep: index.commit() committed the whole staged index; a run could publish unrelated uncommitted work. Fixed with pathspec-scoped commits + a regression test.
  • Vendor rug-pull: gemini-2.0-flash free-tier quota silently went to 0 — extraction returned 0 insights with exit code 0. Diagnosed via the quota error, switched to gemini-2.5-flash.
  • Test pollution: orchestrator tests omitted a path arg and wrote fake runs into the real run_log.json. Isolated to tmp dirs, purged 19 fake entries.
  • Swallowed exceptions: HackerNews errors were silently caught, so the dashboard showed a green step for a failed fetch. Let them propagate.
  • Data migration: renamed a status enum (pushed→published); old manifest.json files crashed on load until a field_validator migrated them.
  • Static-mount 404: draft images referenced a route with no mount — added /drafts-files.

Trend Engine

Daily multi-source trend pipeline → ranked Top-100 + content briefs

AIInfra
Python · HN/Reddit/YouTube/Wikipedia collectors · LLM dedup · SQLite · stdlib http.server dashboard

Collects viral signals from four platforms, scores them, deduplicates + explains them with an LLM pass, and publishes a ranked report with per-platform content briefs. A zero-dependency (http.server) dashboard shows the pipeline stages lighting up live.

What you learned

  • Real-world ETL resilience: per-item batch isolation so one bad record doesn't sink a stage.
  • Working with rate limits, not against them — pacing and RSS fallbacks.
  • Cold-start problems in scoring (percentile ranking with little data).

Approach you took

  • LLM as a dedup/enrichment pass over clustered signals, with enum-fallback validation.
  • Run-row logging + guaranteed DB-connection close even on stage crash.
  • Shared User-Agent header across collectors to stay within platform etiquette.

Alternatives that exist

  • Orchestrators (Airflow, Dagster, Prefect) for scheduled pipelines — heavier, but real observability and retries. You hand-rolled for simplicity.
  • Official APIs vs RSS/scraping — you fell back to Reddit RSS when JSON was blocked for unauthenticated clients (a real constraint, well handled).

Bug classes handled

  • HTTP 429 rate limits → paced fetches + RSS fallback.
  • Resource leaks → close DB connection and log a run row on crash.
  • Security: safe href schemes (avoid injection), idempotent DB saves (no dupes on re-run).
  • Variable shadowing, cross-cluster dedup guards, enum-fallback validation.

Financial Statement Parser (expense_tracker)

Bank statements → structured exports, and the file never leaves the browser

FrontendAI
React · Vite · Tesseract.js (WASM) · pdf.js · Gemini 2.5 Flash · SheetJS · jsPDF

OCR runs entirely in-browser via WebAssembly; only extracted text (never the file) is sent to Gemini for categorisation; user exports CSV/Excel/PDF with analytics. Zero server, zero subscription, zero data liability.

What you learned

  • Client-side heavy compute: running OCR (Tesseract) as WASM in the browser.
  • Privacy as an architectural constraint that drives every decision, not a feature bolted on.
  • PDF rendering pipeline (pdf.js → canvas → image → OCR).

Approach you took

  • Send only text (capped at 8k chars) to the LLM — minimises data exposure and token cost.
  • All persistence and export happen locally in the browser.

Alternatives that exist

  • Server-side OCR (Google Vision, AWS Textract, Docparser) — far more accurate, but receives the user's financial documents. Your whole thesis is not doing that.
  • Cloud LLM vision (send the image directly to a multimodal model) — simpler, but re-introduces the upload you designed away.

Bug classes handled

  • OCR noise on low-quality scans → text cleanup before the LLM step.
  • Large-file / memory limits in-browser (20MB cap, per-page rendering).

Blog — Astro static documentation engine

Folder of Markdown → full docs site, no runtime server

Frontend
Astro · vanilla JS · IntersectionObserver · import.meta.glob

Drop Markdown into a folder; the build produces auto-sidebar navigation, client-side full-text search, scroll-spy TOC, and dark mode. The entire dist/ is static HTML — no backend, no DB.

What you learned

  • Build-time vs runtime separation — compute the sidebar, search index, and routes at build, defer nothing.
  • Algorithms without a library: a ~80-line weighted-scoring search engine, recursive tree-building for the sidebar.
  • IntersectionObserver with tuned rootMargin for scroll-spy.

Approach you took

  • import.meta.glob() as a build-time filesystem API — one primitive feeds both sidebar and search.
  • Zero runtime attack surface: nothing to exploit because nothing runs server-side.

Alternatives that exist

  • Docusaurus / VitePress / MkDocs do this out of the box; building it proves you understand the machinery.
  • Search: your vanilla scorer vs Pagefind, FlexSearch, or Algolia — libraries scale better; yours has zero deps.

Bug classes handled

  • Route/path edge cases when converting file paths to URLs.
  • Scroll-spy jitter — calibrated rootMargin so the right heading highlights.

Bug taxonomy — the classes you've actually handled

This is the section that turns "I fixed a bug" into "I recognise this category of failure." Each is drawn from real commits across your projects.

1. LLM output is malformed / untrusted

Malformed JSON, markdown code fences, dropped fields, hallucinated content.

Where: EMS 4-strategy parse chain; ContentPilot draft/approve gate; Bias auditor blind judge. General fix: validate (Pydantic), retry with a stricter prompt, gate behind a human, or constrain decoding.

2. Silent failure / swallowed errors

A caught exception hides a real failure; the system reports success while doing nothing.

Where: HackerNews exceptions swallowed → green dashboard step for a failed fetch; Gemini quota=0 returned 0 insights with exit code 0. General fix: let errors propagate to a handler that records them; never conflate "ran" with "succeeded."

3. Over-broad side effects

An operation touches more than it should.

Where: git index.commit() committed the whole staged index instead of one file. General fix: scope the operation explicitly (pathspec-scoped commit) + a regression test proving the blast radius is contained.

4. Test / environment contamination

Tests mutate real state; the environment isn't isolated.

Where: orchestrator tests wrote into the real run_log.json. General fix: inject paths, use tmp_path fixtures, never let a test default to a production file.

5. External-dependency instability

Rate limits, auth changes, vendor rug-pulls, blocked endpoints.

Where: Reddit 429 → RSS + pacing; Reddit JSON blocked for anonymous clients; Gemini free tier removed. General fix: back-off/pacing, fallbacks, provider-swap via config, graceful degradation.

6. Data / schema migration

Old persisted data no longer matches new code.

Where: renamed status enum crashed old manifest.json files. General fix: a validator/migration that upgrades legacy records on read.

7. Resource lifecycle & concurrency

Leaked connections, blocking the event loop, thread timing.

Where: DB connection left open on stage crash; BackgroundTasks + blocking calls → explicit threads; sync work must not block FastAPI's loop → run_in_executor. General fix: ensure cleanup on all paths; keep blocking work off the event loop.

8. Non-determinism in evaluation

One stochastic sample is treated as a reliable signal.

Where: prompt tests and bias runs average N samples; statistical significance testing. General fix: multiple runs + aggregation / significance, not a single reading.

9. Web plumbing

Static mounts, safe URL schemes, idempotency.

Where: draft-image 404 (missing mount); safe href schemes; idempotent DB saves. General fix: mind the boundary between routes and static assets; make re-runs idempotent.

Honest gaps — what to learn next (and what an interviewer may probe)

Thin spots across the portfolio

  • Scale & load — everything runs single-user/local. No load testing, horizontal scaling, or p99-latency stories yet.
  • Observability — you log to JSON/DB rows; no metrics/tracing (Prometheus, OpenTelemetry).
  • Auth & multi-tenancy — dashboards are localhost, no real authn/authz.
  • Cloud/CD — Vercel deploys exist; no containers-in-prod, IaC, or k8s story.

Highest-leverage next steps

  • Add real observability to one project (metrics + a trace) — it's the most-asked "what's missing" in AI-infra interviews.
  • Load-test the LLM Eval Framework and get a real throughput/latency number to quote.
  • Containerise + deploy one service to a cloud with IaC, end-to-end.
  • Pick one project to take from POC to genuinely production-hardened, rather than starting a new one.
