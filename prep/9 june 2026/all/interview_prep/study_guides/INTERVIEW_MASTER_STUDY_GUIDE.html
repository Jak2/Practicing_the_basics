How to study this guide

Six learning techniques with the strongest evidence behind them. Don't read passively — the whole point is to retrieve, not re-read.

01

Active recall

Close the tab. Explain the topic out loud. Only reopen to check what you missed. Recall > re-reading, every time.

03

Feynman technique

Teach it to a rubber duck in plain words. The sentence you stumble on is the gap. That's your interview weak spot too.

04

Interleaving

Don't block one topic all day. Mix LangGraph + a system-design question + a Python trick. Mixing builds discrimination.

Build to learn

Guided walkthroughs — tell it like a story

This is the section to read out loud. Read one top to bottom and you've just rehearsed the "tell me about this project" answer. No jargon without a plain-English gloss right next to it.

How to use in the room: open with the one-line analogy, then walk the numbered steps as a flow ("first… then… the reason I did this and not that…"). Steps 1→N are your answer. If they go deeper on any step, that's where the Textbook entry kicks in.

1 · 5G Failure-Detection Pipeline

Analogy: a doctor for the network. It reads the "symptoms" in the traffic logs, looks up similar past cases, and suggests the cure.

The 30-second version: engineers used to spend hours reading raw 5G packet captures to figure out why a call or handover failed. I built a pipeline that reads the capture, finds the error, matches it against a library of known errors, and asks an LLM to write the fix — dropping analysis from hours to seconds.

  1. STEP 1 — read the capture. A .pcap file is a recording of network traffic. I use Pyshark (a Python wrapper over Wireshark) to open it and pull out only the signaling messages — the control messages phones and towers exchange. I filter as I read so I'm not loading gigabytes into memory.
  2. STEP 2 — identify the error. Each message belongs to a protocol layer (NAS, NGAP, RRC, Diameter…). I detect the layer and extract the specific failure — an authentication timeout, a dropped handover, congestion.
  3. STEP 3 — find similar known errors. I turn the error text into an embedding — a list of numbers that captures its meaning — and search a vector database (Qdrant) of ~200 known error patterns for the closest matches. This is semantic search: it finds errors that mean the same thing even if worded differently.
  4. STEP 4 — the key decision: filter first. Before ranking by similarity, I filter by vendor and layer inside the database. This is why I chose Qdrant over the more common FAISS: FAISS can't filter during search, so a very similar Ericsson fix could surface for a Nokia error. Filtering first makes that mistake impossible.
  5. STEP 5 — write the fix. I feed the matched patterns to Claude through LangChain's RetrievalQA (a helper that bundles "here's the question + here's the retrieved context" into one call) and it writes a contextual fix suggestion grounded in the real matches — not made up.
  6. STEP 6 — spend money wisely. If the match is confident and the issue isn't critical, I use the cheap fast model (Haiku); only hard or critical cases go to the expensive one (Sonnet). Three simple checks, ~60% lower API cost.
  7. STEP 7 — get smarter over time. If an error matches nothing well, I log it to a separate "unknown errors" collection for a human to review — so the knowledge base grows.
The one line they'll remember: "The whole design hinges on filtering the search by vendor at the database level — that's a correctness guarantee, not a preference, and it's the reason I picked Qdrant over FAISS."

2 · NFTRACE

Analogy: a control tower for network testing. It tells many recorders to start together, keeps each test's recording separate, and checks the results automatically.

The 30-second version: testing 5G means capturing traffic across several network boxes at the same time, then checking the protocol flows were correct. I built a REST service that orchestrates those captures, keeps parallel test runs from colliding, and validates the flows automatically inside Nokia's CI — cutting validation time in half.

  1. STEP 1 — one clean interface. I expose a simple FastAPI REST API: start, stop, merge, validate. Callers don't need to know the messy details underneath.
  2. STEP 2 — talk to the old boxes. The network nodes only speak XML-RPC (an older remote-call protocol). I hide that behind a translation layer, so if we ever move to gRPC, only that one layer changes — the rest of the system doesn't care.
  3. STEP 3 — start them together. I use multiprocessing to tell all the nodes to begin capturing at once, in parallel, rather than one after another.

5 · Bias & Fairness Auditor

Analogy: a controlled experiment for fairness. Change only the name, keep everything else identical, and measure — with real statistics — if the AI treats people differently.

01 · Retrieval & RAG

RAG — Retrieval-Augmented Generation▾

What: instead of trusting the model's memory, you retrieve relevant documents at query time and inject them into the prompt, so the answer is grounded in real data you control.

Why it's strong: it's the fix for two problems at once — hallucination (the model can't make things up if it's answering from retrieved facts) and staleness (you update the knowledge base, not the model). Your 5G pipeline and EMS both use it on real data, not toy demos.

How: embed every document into a vector, store in a vector DB; at query time embed the question, find the nearest vectors (semantic match), stuff the top-k results into the prompt as context, and instruct the model to answer only from that context.

Say it like this → "Retrieval gates generation. The model can only answer from the chunks I retrieved, so 'find a DevOps engineer' matches a resume that says 'managed Kubernetes clusters' even with zero keyword overlap — and if the answer isn't in the retrieved context, it doesn't answer."
Embeddings & vector search (HNSW, cosine)▾

What: an embedding turns text into a fixed-length vector (e.g. 1536-dim for OpenAI ada-002, 384 for MiniLM) where similar meanings sit close together. Search = find nearest vectors.

Why it's strong: it's semantic, not lexical — it understands meaning, so keyword search can't compete. Knowing HNSW and cosine specifically signals you understand the index, not just the API.

How: exact nearest-neighbor is O(n); HNSW (Hierarchical Navigable Small World) is an approximate-NN graph that gets sub-millisecond search by hopping through layered "shortcut" links. Cosine similarity measures the angle between vectors (direction, not magnitude) — the standard for normalized text embeddings.

Say it like this → "I used cosine over HNSW — approximate nearest-neighbor, so retrieval stays sub-millisecond even as the knowledge base grows. Exact search would be linear; HNSW trades a tiny recall cost for a huge speed win."
Metadata pre-filtered retrieval (Qdrant vs FAISS)▾

What: filtering the vector search by structured metadata (vendor = Nokia, layer = NAS) before ranking by similarity, so only valid candidates are ever compared.

Why it's strong: this is your single best "why this DB not that one" story. It's a real correctness decision with a concrete failure it prevents — not a preference.

How: Qdrant applies the filter at the DB level during the HNSW traversal. FAISS has no native filtering — you'd search first, then drop wrong-vendor results in Python, which can leave you with too few or zero valid matches and wastes the search.

Say it like this → "I chose Qdrant over FAISS because I need vendor/layer filtering to run at the DB level before similarity ranking. With FAISS's search-then-filter, a high-similarity Ericsson fix could surface for a Nokia error. Pre-filtering makes that impossible by construction."
Chunking strategy▾

What: splitting documents into pieces (you used 500 chars with 100 overlap) before embedding, because you retrieve chunks, not whole documents.

Why it's strong: chunk size is a real tuning knob interviewers probe — too big dilutes the embedding's meaning, too small loses context. Overlap prevents a fact being split across a boundary.

How: sliding window over the text; the 100-char overlap means a sentence cut at a boundary still appears whole in the neighboring chunk, so retrieval doesn't miss it.

Say it like this → "500/100 was a balance — small enough that each embedding has a tight, specific meaning, with overlap so a fact spanning a boundary isn't lost. If retrieval quality dropped, chunk size is the first dial I'd turn."
Hybrid retrieval + reranking learn this▾

What: the "next layer" of RAG interviewers ask about. Hybrid = combine keyword (BM25) with dense vector search. Reranking = a second, more accurate model reorders the top candidates.

Why it's strong: pure vector search misses exact matches (error codes, IDs, names); BM25 catches those. A cross-encoder reranker then reads query+doc together for far better precision than the bi-encoder embedding.

How: retrieve top-N from both BM25 and dense, merge; pass those N to a cross-encoder that scores each (query, doc) pair jointly; keep the top-k. Measure with recall@k and MRR before/after.

Say it like this → "My current RAG is dense-only. The upgrade is hybrid + rerank: BM25 for exact codes and IDs that embeddings blur, then a cross-encoder reranker for precision. I'd validate it with recall@k on a labelled set, not vibes."

02 · LLM reliability & control

LLM-as-judge (blind, score-recomputed)▾

What: using an LLM to grade another LLM's output against a rubric — but with two guards: strip anything that could bias the judge, and recompute the final score yourself instead of trusting the judge's arithmetic.

Why it's strong: most people use a judge naively. You built defenses into the judge — that's the difference between "I called GPT to score it" and "I designed an evaluator I can trust."

How: give the judge a structured 1–5 rubric and force JSON output. In the Bias Auditor, demographics are removed before the judge sees the pair (blind), so the judge can't import its own bias. In the Regression Suite, you route the judge to a different provider than the model under test (anti-self-bias) and recompute the weighted score in code because LLM math is unreliable.

Say it like this → "A judge is only trustworthy if it can't cheat. So I blind it to demographics, route it to a different model family than the one it's grading, and recompute the final number myself — the LLM produces the sub-scores, my code does the arithmetic."
Hallucination detection (claim decomposition + NLI)▾

What: break the model's answer into atomic claims, then check each claim against the source with a Natural Language Inference model that labels it SUPPORTED / UNSUPPORTED / CONTRADICTED.

Why it's strong: it's a rigorous, decomposable definition of hallucination instead of a vibe. It also runs on a local NLI model, so it's cheap — a cost-conscious design choice.

How: an LLM splits the answer into discrete factual claims; each (claim, source) pair goes to a cross-encoder NLI classifier; any UNSUPPORTED/CONTRADICTED claim flags the answer.

Say it like this → "I decompose the answer into atomic claims and run each through a 3-way NLI check against the source. One contradicted claim fails the whole answer. It's local, so grading a response costs almost nothing."
Faithfulness vs accuracy (the RAG diagnostic)▾

What: two different questions. Faithfulness = did the answer stay within the retrieved context? Accuracy = is the answer actually true? They can disagree.

Why it's strong: this distinction is genuine eval-design nuance most engineers miss, and it's diagnostic — the combination tells you which part of your RAG pipeline is broken.

How: high faithfulness + wrong answer → the retriever fed bad context (retrieval problem). Low faithfulness + right answer → the model answered from its own training memory, ignoring the context (context leakage — dangerous, it'll fail on anything not in training).

Say it like this → "I measure faithfulness separately from accuracy because together they localize the bug: faithful-but-wrong is a retrieval failure; correct-but-unfaithful means the model bypassed my context and got lucky — which won't hold in production."
Structured output + multi-strategy JSON repair▾

What: forcing the LLM to return JSON and then defending against the ~10–20% of the time it returns broken JSON — with a cascade of repair strategies before giving up.

Why it's strong: "the LLM sometimes returns bad JSON" is a real production failure everyone hits; having a layered answer (not one try/except) shows you engineer around non-determinism.

How: EMS chains direct parse → regex-extract the JSON block → cleanup malformed syntax → key-value fallback, then validates with Pydantic and retries with a stricter prompt if a required field is missing. The Finance parser adds truncation repair: strip code fences → match bracket boundaries → salvage the last complete object with graceful field nulling.

Say it like this → "I treat LLM output as untrusted input. Four parse strategies from strict to lenient, Pydantic validation on top, and a stricter-prompt retry if a required field is missing — so a malformed response degrades to a partial result, never a crash."
Handling non-determinism (multi-run + flakiness)▾

What: because an LLM gives different answers to the same input, one sample is an unreliable signal. You run N times and aggregate, and flag prompts whose outputs vary too much.

Why it's strong: it shows you treat the LLM as a stochastic system and apply basic statistics — the same instinct that separates a real eval from a demo.

How: run each case 3× and average the scores; compute std-dev and flag "flaky" if it exceeds a threshold (0.05). For determinism where you can get it, set temperature=0 and a fixed seed (EMS extraction).

Say it like this → "One LLM response at temperature 0.7 is noise. I average three runs and flag high-variance prompts as flaky — a flaky prompt is a reliability bug even if its average passes."
Confidence-based model routing (cost control)▾

What: sending easy cases to a cheap fast model (Haiku) and only escalating hard/critical ones to an expensive model (Sonnet), decided by a simple rule.

Why it's strong: it's cost engineering with a real number attached (~60% cut) and no ML complexity — three booleans. Interviewers love a candidate who thinks about token economics.

How: if retrieval similarity > 0.92 AND the score gap to the next match > 0.15 AND severity is non-critical → Haiku; otherwise Sonnet. High confidence + clear winner + low stakes = safe to use the cheap model.

Say it like this → "I route by confidence: when retrieval is unambiguous and the case isn't critical, Haiku handles it at 3–5× lower cost and latency; ambiguous or high-severity cases escalate to Sonnet. Three booleans, ~60% cost saved, no accuracy loss where it matters."
Hybrid LLM + deterministic (the "don't ask the LLM everything" pattern)▾

What: use the LLM only for the part that's genuinely unpredictable (understanding natural language) and deterministic code for the part that's fixed (generating exact syntax), with a regex fallback if the LLM fails.

Why it's strong: this is the clearest senior-judgment story you have. Junior instinct is "make the LLM do the whole thing." You drew the line at exactly the right place and guaranteed uptime.

How (RF generator): Claude Haiku extracts entities from the English description (unpredictable); str.format() templates fill the rigid Robot Framework syntax (fixed); the real RF parser validates it will run; if the LLM call fails, regex extraction takes over so output never stops.

Say it like this → "I don't ask the LLM to generate the whole file — that's unreliable and expensive. The LLM only interprets the natural-language intent; deterministic templates produce the exact syntax; the real parser validates it; and regex is the fallback so a bad LLM response never breaks the tool."
Human-in-the-loop approval gate▾

What: the AI proposes, a human approves before anything irreversible happens — a draft/approve step in front of publishing, committing, or acting.

Why it's strong: it's the mature answer to "how do you deploy AI you can't fully trust?" It shows you design for the model being wrong, which is exactly what safety-conscious teams want.

How: generated output is written to a pending/draft state, surfaced in a UI for review, and only promoted (git commit + push, DB write) on explicit approval; reject discards it with no side effect.

Say it like this → "Anything the model produces lands as a draft first. A human approves or rejects before it's published — so a hallucinated output can't reach production. Full autonomy is an opt-in flag, not the default."

03 · Systems, concurrency & scale

Async job architecture (broker/worker: Celery + Redis)▾

What: the API accepts a request, drops a job on a queue, and returns immediately (HTTP 201); separate worker processes pull jobs and do the slow work (LLM calls, evals).

Why it's strong: it's the standard scale-out pattern and you can justify why a queue over a background task — durability. A dropped in-process task silently fails; a queued job survives a worker crash and retries.

How: FastAPI validates + enqueues to Redis (broker) → returns 201 → Celery workers (concurrency N) consume, run evaluators, write results to Postgres, retry 3× on failure, alert Slack on regression. Scale by adding workers.

Say it like this → "I used Celery over FastAPI BackgroundTasks because this is a CI quality gate — it has to be durable. A background task dies with the process; a queued job survives a crash and retries. The caller never waits, and I scale by adding workers."
asyncio + Semaphore rate limiting▾

What: firing many LLM/API calls concurrently but capping how many run at once, so you're fast without hitting rate limits.

Why it's strong: it shows you understand the difference between concurrency and uncontrolled parallelism — the Bias Auditor fires 500 calls (100 variants × 5 runs) without getting throttled.

How: an asyncio.Semaphore(10) lets at most 10 coroutines past the gate at once; each awaits the LLM call and releases on completion, so you keep 10 in flight continuously instead of serializing or flooding.

Say it like this → "A Semaphore caps concurrency at 10 — full throughput without tripping the provider's rate limit. It's the middle ground between serial (too slow) and unbounded gather (instant 429s)."
Polyglot persistence▾

What: using more than one type of database, each for the job it's best at, instead of forcing one to do everything.

Why it's strong: it's a deliberate data-modeling decision you can defend per store — and you can also name the cost (cross-store consistency), which shows maturity.

How (EMS): Postgres for structured employee records (relational queries, transactional updates); MongoDB GridFS for raw PDF/image files (binary blobs don't belong in a relational DB); FAISS for vector embeddings (sub-ms semantic search SQL can't do).

Say it like this → "Three stores, one job each: Postgres for structured queries and transactional writes, GridFS for the raw files, FAISS for semantic search. The tradeoff is cross-store consistency on partial failure — a genuine distributed-systems problem I'd solve with an outbox pattern."
Two-tier hot/cold storage (Redis + SQLite)▾

What: fast ephemeral state in Redis (hot), durable audit history in SQLite (cold) — split by access pattern, not by habit.

Why it's strong: you can reason about it bidirectionally, which is what interviewers listen for: "if I used only Redis I'd lose the audit trail on restart; if I used only SQLite every concurrent worker read would hit disk."

How (NFTRACE): live session state in Redis with a TTL (setex, 3600s) for sub-ms reads and automatic cleanup; permanent records (sessions, nodes, validation results) in SQLite with a foreign-key schema for querying history.

Say it like this → "Hot mutable session state lives in Redis with a TTL; the cold audit trail lives in SQLite. Redis alone loses history on restart; SQLite alone can't take concurrent sub-millisecond reads. The split matches the access pattern."
gRPC model gateway + multi-provider routing (Brane)▾

What: a single gRPC service that all callers hit for inference; it routes to the right model provider (instruct / thinking / vision) behind one contract, and scales statelessly.

Why it's strong: gRPC + a gateway is a systems-engineering signal most AI candidates lack. Stateless = you can horizontally scale by adding replicas, no sticky sessions.

How: gRPC (HTTP/2, binary protobuf, low latency) exposes one inference RPC; the gateway picks the provider/model by request type; because it holds no per-request state, a load balancer can spread traffic across N identical replicas.

Say it like this → "One gRPC gateway fronts every model provider behind a single contract, routing by task type — instruct, thinking, vision. It's stateless, so scaling is just more replicas behind a load balancer. gRPC over REST for the low-latency binary protocol on a hot path."

Why it's strong: it's the answer to every "you have no auth" gap in your other projects — you have built serious authorization, just elsewhere. Fine-grained RBAC is enterprise-grade.

How: permission rows in Postgres map (role/agent → attribute → allowed action); a cache avoids re-checking on every field access (the caching was a real perf optimization you made).

Say it like this → "At Brane I built attribute-level RBAC — permissions down to individual fields, with a cache so we're not re-checking on every attribute access. So when you ask how I'd secure the HR system: JWT for identity, this RBAC model for authorization."
Facade over a legacy protocol + saga/outbox▾

What: two "designing for change / correctness" patterns. Facade: wrap an ugly external constraint (nodes only speak XML-RPC) behind a clean interface. Saga/outbox: keep multiple stores consistent when one write can fail.

Why it's strong: the facade shows you isolate change (a future gRPC migration touches one layer). Naming saga/outbox as the fix for your EMS cross-DB gap turns an admitted weakness into a design conversation.

How: facade — a NodeManager translates clean REST calls into XML-RPC per node. Outbox — write the intended change to an "outbox" table in the same transaction as the primary write, then a separate process reliably delivers it to the other store, so nothing is lost on partial failure. Say it like this → "The nodes only speak XML-RPC, so I hid that behind a REST facade — a future gRPC swap touches one layer. And for the Postgres-then-FAISS consistency gap: an outbox pattern, where the index update is written transactionally and delivered reliably, is how I'd close it."

Build-time vs runtime (SSG)▾

What: computing everything you can when the site is built (sidebar tree, search index, routes) so nothing is deferred to when a user loads the page — zero backend at runtime.

Why it's strong: a clean mental model interviewers test, plus a security angle: no runtime server means no runtime attack surface.

How (Astro): import.meta.glob() discovers all Markdown files at build time; that one primitive feeds both the sidebar tree and the search index, which are baked into static HTML. The output is pure files any CDN serves.

Say it like this → "Anything computable at build time, I compute at build time — the sidebar, the search index, the routes. The result is static HTML with no runtime server, so it's instant from a CDN and has no server-side attack surface."

Landmine answers — rehearse these cold

Three questions cut across every project and can sink a strong interview. Each has one honest answer you reuse. Say them out loud until they're automatic — a prepared honest answer reads as senior; a scramble reads as risk.

📏

"How did you measure that?"

Every % (70% auto-resolve, 55% MTTR, 50% validation, ~60% cost) is an internal operational metric vs a manual baseline — not a controlled study. Say exactly that, describe how you counted, over what window. Never invent an A/B test.

📈

"How does it scale?"

Your Celery/async/sharding/worker-pool scale-outs are designed, not built or load-tested. Say "proposed, not shipped," then reason through it live. Implying it's in prod is the trap.

🧪

"How did you test it?"

Telecom projects have real 3-tier testing — lead with those. Personal projects (Finance, Blog) have none — acknowledge it, say what you'd add. Don't bluff a suite that isn't there.

Read-the-code risk: some deep-dive snippets are illustrative, not verbatim (NFTRACE's SIP rule always-fails on REGISTER; BackgroundTasks imported-but-unused in the 5G pipeline). If an interviewer reads a snippet literally, say plainly it's a simplified/representative excerpt, not production code.
