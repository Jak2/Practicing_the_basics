01Foundations

What is prompting?

A prompt is the complete input you give an LLM. Prompt engineering is designing that input to produce a desired output reliably, efficiently, and safely. Part linguistics, part psychology, part systems design.

Anatomy of a complete prompt
Core mental model

The model does not understand - it predicts

LLMs are next-token prediction engines. They have no intent, no understanding, no goals. What they have is an extremely powerful statistical model of "given this sequence of tokens, what comes next?" Every PE technique works by shaping that input so the statistically likely continuation is the output you want. Once you internalize this, prompting becomes intuitive.

What prompting IS
  • Designing input sequences that steer token prediction
  • Providing context the model lacks but needs
  • Constraining output distribution to useful regions
  • Teaching output format through examples
  • Eliciting reasoning before the final answer
What prompting is NOT
  • Programming the model with explicit logic
  • Reliable without systematic testing and iteration
  • A substitute for fine-tuning on fundamental behavior changes
  • Injecting new knowledge the model never learned
  • Deterministic - same prompt can yield different output

Every SAP AI application built on SAP BTP Generative AI Hub or using Joule (SAP's enterprise copilot) uses this exact prompt anatomy under the hood. Understanding it lets you take control instead of relying on defaults.

  • System prompt → SAP context injection: In Joule and BTP AI SDK, the system prompt is where you inject your company's business context — org structure, permitted data sources, SAP module scope (FI, MM, SD, HR), and compliance rules. A well-designed system prompt can eliminate 60–70% of hallucinations in SAP process answers.
  • Injected context → SAP data layer: In BTP, context injection pulls from SAP HANA Cloud vector tables, SAP Knowledge Graph, or live RFC/BAPI responses. The context block is where live inventory levels, open POs, or GL account balances get pulled at inference time.
  • Output format spec → ABAP-consumable JSON: Defining strict JSON output schemas means Joule's responses can be directly parsed by ABAP REST consumers or BTP integration flows without post-processing.

04Prompt Engineering

Prompt engineering principles

The laws governing effective prompting across all models. Every technique is a specific application of one or more of these fundamental principles.

Seven principles of effective prompting
mindmap root["7 PE Principles"] Clarity Be explicit about exactly what you want Avoid ambiguous pronouns and vague terms Define terms the model might misinterpret Context Models lack your context by default Provide what is relevant not everything you know Relevance beats raw volume every time Constraint Limit output format early in the prompt Specify what TO do rather than what not to do Use stop sequences and JSON schema for structure Examples One example beats 100 words of instruction Include both positive and negative examples Keep consistent formatting across all examples Reasoning Ask model to think before answering Chain-of-thought improves accuracy on hard tasks Externalize scratchpad before final answer Role Expert persona shifts the statistical distribution Be specific about expertise level and domain Roles activate dormant domain knowledge Iteration Prompts are hypotheses not finished solutions Test on diverse inputs including edge cases Measure before and after every change you make
Principle: Be explicit

Specificity is free

Every ambiguity is resolved by the model using statistical likelihood which may not match your intent. "Write a summary" is underspecified. "Write a 3-sentence executive summary focused on business impact, written for a non-technical audience using no jargon" is specific. The extra 20 words can make the difference between useful and useless output.

Principle: Show, don't tell

Examples outperform instructions

One well-chosen input-output example communicates more about desired behavior than a paragraph of instructions. The model has seen billions of examples during training and recognizes patterns instantly. Instructions must be parsed and mapped to behavior. Examples are directly in the training distribution.

Advanced
Positive constraints outperform negative onesTelling the model what NOT to do is less reliable than telling it what TO do. "Do not use bullet points" fights the training distribution. "Write in flowing prose paragraphs" works with it. Default to positive framing in all prompt constraints.
SAP SAP-specific prompt engineering principles Critical

The seven PE principles apply with SAP-specific nuance. The SAP domain has unique terminology, process semantics, and data structures that must be handled explicitly in prompts.

  • Clarity → use SAP terminology precisely: "Create a PR" means purchase requisition in SAP — not a GitHub pull request. Prompts for SAP workloads must define all abbreviations in the system prompt (ME51N, VA01, FB50, etc.) or the model will guess incorrectly from its general training.
  • Context → inject live SAP data, not just descriptions: Don't describe what the data looks like — inject the actual SAP data. Pull the open sales order list from SD, the current stock level from MM, or the vendor payment terms from FI, and put the actual values in the context block.
  • Role → SAP functional consultant persona: Assigning an expert persona like "You are a certified SAP FI/CO consultant with 10 years of S/4HANA implementation experience" measurably improves answers on SAP process questions. The model has been trained on SAP documentation and certification materials — this role activates that knowledge.
  • Examples → SAP transaction outputs: Few-shot examples for SAP tasks should use real SAP transaction output formats (e.g., ALV grid layouts, IDoc segment structures, BAPI return tables) so the model learns to reason in SAP-native formats.
  • Usecase — SAP SuccessFactors HR chatbot: System prompt assigns "SAP SuccessFactors HR specialist" persona. Positive examples show correct leave balance queries and policy answers. Negative examples show what NOT to do (e.g., never advise on local labor law specifics — always redirect to HR). Result: 85% reduction in HR query escalations.

06Advanced Prompting

Context engineering

The next evolution beyond prompt engineering. PE focuses on the instruction. Context engineering focuses on what information occupies the model's context window - in what order, format, and density.

Context window as a managed resource
graph LR CW["Context Window 128K to 1M tokens"] --> SYS2["System prompt: high weight, processed first by model"] CW --> HIST["Conversation history: decaying relevance over time as turns grow"] CW --> DOCS["Retrieved documents: gold if relevant, noise if not"] CW --> TOOL["Tool results: often verbose, needs truncation before injection"] CW --> MEM["Memory summaries: compressed prior context from previous sessions"] CW --> USR2["User message: high recency weight, model attends strongly"] DOCS --> OPT["Position matters critically: primacy and recency effects are real"] MEM --> OPT TOOL --> OPT OPT --> RULE["Most critical information belongs at START or END of context window"] style CW fill:#0d1117,stroke:#f0c040,color:#e6edf3 style OPT fill:#0d1117,stroke:#ff6b6b,color:#e6edf3 style RULE fill:#0d1117,stroke:#4ade80,color:#e6edf3
Context density

Signal-to-noise ratio

Every irrelevant token is noise. The model attends to everything and cannot know in advance which parts matter. Dense relevant context beats long padded context. Chunk documents to relevant sections only. Summarize history rather than appending raw turns. Truncate verbose tool outputs. Remove boilerplate from retrieved web pages.

Context position

Primacy and recency effects

LLMs have strong attention at the beginning and end of context. Information buried in the middle of long contexts is statistically underweighted. This is the lost-in-the-middle problem confirmed by research. Critical instructions belong at the start. Most relevant retrieved chunks belong closest to the user message.

Context engineering strategies

The practitioner toolkit

  • Hierarchical summarization: Recent turns verbatim, older turns summarized, ancient turns as key facts only. Progressive compression prevents context overflow.
  • Dynamic context assembly: Retrieve relevant documents per query rather than loading everything upfront. RAG is context engineering.
  • Context pruning: Before each LLM call, score context chunks for relevance to current query and drop low-score chunks entirely.
  • Structured context: Use XML or JSON to separate context types. Helps the model parse and weight them correctly without confusion.
  • Instruction repetition: For very long contexts, repeat critical instructions both at the start and immediately before the user message.

# Command router - how /commands and @mentions activate skill files at runtime
import re
from pathlib import Path

class AgentCommandRouter:
    def __init__(self, skills_dir: str, personas_dir: str):
        self.skills_dir = Path(skills_dir)
        self.personas_dir = Path(personas_dir)

    def parse(self, user_input: str) -> dict:
        commands = re.findall(r"/([a-z-]+)", user_input)
        mentions = re.findall(r"@([a-z-]+)", user_input)
        clean = re.sub(r"[/@][a-z-]+", "", user_input).strip()
        return {"commands": commands, "mentions": mentions, "message": clean}

    def build_system_prompt(self, commands: list, mentions: list, base: str) -> str:
        sections = [base]
        for cmd in commands:
            skill_file = self.skills_dir / cmd / "SKILL.md"
            if skill_file.exists():
                sections.append(f"## Active skill: {cmd}\n{skill_file.read_text()}")
        for mention in mentions:
            persona_file = self.personas_dir / f"{mention}.md"
            if persona_file.exists():
                sections.append(f"## Active persona: {mention}\n{persona_file.read_text()}")
        return "\n\n---\n\n".join(sections)

What are LLM agents?

An LLM agent is a system where the language model acts as a decision-maker. It receives a goal, reasons about how to achieve it, calls tools, observes results, and iterates until the task is complete or it cannot proceed further.

Agent vs pipeline - the critical distinction

Dynamic decision-making is what makes something an agent

A pipeline is a fixed sequence of LLM calls - step 1 always calls A, step 2 always calls B. An agent decides at runtime which actions to take based on what it observes. The number of steps, which tools are called, and whether to ask for clarification are all determined by the model's reasoning at runtime, not by the programmer's hardcoded sequence. This is what makes agents powerful - and, if poorly designed, unpredictable and expensive.

When agents excel

  • Tasks where the number of steps is unknown upfront
  • Tasks that require adapting to unexpected intermediate results
  • Research tasks where follow-up depends on what you find
  • Tasks requiring judgment about which tool or approach to use
  • Tasks that need error recovery and alternative path selection

When pipelines beat agents

  • Well-defined fixed workflows with known step count
  • Latency-critical paths where dynamic overhead is unacceptable
  • Cost-sensitive applications where agent exploration is too expensive
  • Compliance contexts needing fully auditable deterministic execution
  • Simple tasks where agent overhead dwarfs the work itself

@dataclass
class AgentMemorySystem:
    working_memory: list[dict]         # Current context window messages
    episodic_store: Any                # VectorStore - past interactions (Chroma, Pinecone)
    semantic_store: Any                # VectorStore - facts and knowledge base

Model Context Protocol (MCP)

The universal tool standard - how it works internally

  • MCP server: exposes tools, resources, and prompts via standard JSON-RPC. Each tool has a name, description, and input schema identical to the function calling format above.
  • MCP client: the LLM runtime. Discovers tools from connected servers, injects their schemas into model context, and routes tool_use calls to the correct server.
  • Transport: stdio for local subprocess tools, SSE for remote HTTP servers, WebSocket for bidirectional streaming connections.
  • Resources: files, database rows, API responses - things the model can read without calling a function.
  • Why it matters: write one MCP server per tool and any MCP-compatible agent runtime connects to it instantly. This is why Claude connects to Google Drive, GitHub, Slack, or your custom database without bespoke integration code in the agent itself.

        call_llm_async(WORKER_MODEL, "Execute task", subtask) 
        for subtask in plan
    ])
    
    # Critic: use smart model for accurate quality judgment
    score = call_llm(CRITIC_MODEL, "Score quality 1-10", "\n".join(results))
    
    # Synthesis: use smart model for final coherent output
    return call_llm(ORCHESTRATOR_MODEL, "Synthesize into final output", "\n".join(results))

When to use multi-agent

  • Task exceeds one context window in complexity
  • Subtasks need different expertise or tool sets
  • Parallelism can reduce wall-clock time significantly
  • Independent verification adds real quality (critic pattern)

Agentic orchestration

Orchestration is the control plane — which agents run, in what order, with what inputs, and what happens to their outputs. The orchestrator is itself an LLM making routing decisions at runtime.

The four orchestration patterns

Sequential, parallel fan-out, map-reduce, conditional

  • Sequential: Task A completes then B starts. Output of A feeds into B. Simple to implement and debug. Slow because nothing runs in parallel.
  • Parallel fan-out: Multiple agents work simultaneously on independent subtasks. Orchestrator collects and merges all results. Requires truly independent subtasks — any dependency breaks it.
  • Map-reduce: Orchestrator maps a task across N agents, then reduces all outputs into one result. Best for large document analysis or multi-source research tasks.
  • Conditional branching: Orchestrator evaluates a condition — confidence score, task type, previous result quality — and routes to different agents. Like a switch statement powered by LLM judgment.

SYSTEM = """You are a research assistant.

SAP Prompt injection risks in SAP AI systems Critical Security Risk

Prompt injection in SAP contexts has direct financial and compliance consequences. An injected instruction that creates a fraudulent purchase order or alters a payment run is not just a security incident — it is a financial crime.

  • SAP GRC integration for AI agent actions: Before any AI agent executes a write action in SAP (create PO, post journal entry, approve payment), route the proposed action through SAP GRC Access Control for automated risk analysis. Reject or escalate if the action would violate an SoD rule.
  • Audit trail mandatory: Every AI agent action in SAP must be logged with the full prompt context, the tool called, the parameters passed, and the SAP document created. This is a legal requirement in most regulated industries using SAP (financial services, pharmaceutical, public sector).
  • Usecase — Defended SAP AP automation: Invoice PDF is processed in a sandboxed extraction agent (read-only tools only). Extracted data is validated against vendor master. Prevention checklist

  • Set max_iterations on every agent loop without exception
  • Validate all inter-agent messages with Pydantic schemas always
  • Hard truncate tool outputs before injecting into context
  • Log every tool call with full input, output, and latency
  • Test agents on adversarial and edge case inputs before shipping
  • Add circuit breakers: if error rate exceeds threshold, halt and alert
  • Implement correlation IDs from day one, not as an afterthought

Root causes of most failures

  • No iteration limit set - infinite loops guaranteed to happen eventually
  • Untyped inter-agent messages - ambiguous payloads cause misinterpretation
  • Verbose tool output injected raw - overflows context window silently
  • No correlation IDs - impossible to trace failure to its origin agent
  • No offline eval suite - failures first discovered in production by users
  • Mixing trusted instructions with untrusted retrieved content in same prompt
  • Using expensive smart model for every step - unsustainable at scale
SAP Failure modes in SAP agentic systems High Stakes — SAP Data Integrity at Risk

Agent failures in SAP have downstream consequences that compound through the process chain. A hallucinated PO number, wrong GL account, or incorrect tax code can cascade into financial misstatements, audit findings, and regulatory risk.

  • Hallucinated SAP document numbers: Agents may generate plausible-looking but non-existent SAP document numbers. Defence: always validate document numbers against SAP via a READ tool call before using them in downstream actions. Never trust an AI-generated SAP key without database verification.
  • Wrong GL account suggestion: AI suggesting the wrong GL account for journal entries is a common failure that causes financial misstatements. Defence: build a GL account validation tool that checks proposed accounts against the chart of accounts and cost element categories before allowing posting.
  • Context overflow in SAP master data: SAP material masters, vendor masters, and customer masters are verbose. Feeding an entire master record into the context window wastes tokens and buries the relevant fields. Defence: extract only the relevant fields per use case using a structured template.
  • Infinite loops in SAP approval workflows: An agent trying to route an approval that keeps failing authorization checks can loop indefinitely, creating repeated workflow items in SAP. Defence: max_iterations plus a "park and escalate" action that creates an SAP workflow task for human resolution.
  • Usecase — Safe SAP FI posting agent: Before posting any journal entry, the agent calls: validate_gl_account(), check_posting_period_open(), verify_cost_center_assignment(), confirm_tax_code_validity(). Only if all four checks pass does it call the posting BAPI. Any failure creates an SAP notification for the FI team rather than attempting a workaround.
