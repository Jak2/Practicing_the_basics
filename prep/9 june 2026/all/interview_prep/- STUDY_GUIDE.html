The plan — 4 tiers, by leverage

Don't study in the order things feel comfortable. Study in the order that wins interviews: highest demand × biggest gap first. Interleave — do a little from two tiers each day rather than finishing one topic before starting the next; mixing is what builds durable recall.

TIER 0 Do before your next interview ~1 week, highest ROI
① System design at scale — the #1 demand (14 JDs) and your thinnest real answer.
② The "how did you measure that" answer — one honest script for all your % metrics.
③ Own your self-disclosed gaps — cross-DB consistency, the bias weight bug, no-auth.
④ Fine-tuning literacy — LoRA/PEFT concept + one tiny run to claim hands-on.
TIER 1 Strengthen the thin-but-demanded ~1–2 weeks
⑤ Observability — logs→metrics→traces; wire Prometheus+Grafana into one project.
⑥ AWS refresh — you have AppSync/IAM from 2022; add ECS/Lambda/S3 mental model.
⑦ CI/CD depth — you have GitHub Actions + Nokia NCD; be able to design a pipeline.
⑧ LangGraph — bridge from your hand-rolled agent loop to the named framework.
TIER 2 Breadth & literacy ongoing
⑨ Kubernetes as operator — you tested on K8s; learn to deploy to it.
⑩ Classic ML literacy — enough sklearn/metrics to not freeze on "precision vs recall."
⑪ Cloud breadth — Azure/GCP conceptual equivalents of what you know in AWS.
⑫ MLOps / serving — vLLM, model registry, the shape of a deployment pipeline.
TIER 3 Deflect gracefully, don't cram know the edges
Deep PyTorch model architecture · Snowflake · Kafka internals · research-grade math. For these, the winning move isn't cramming — it's an honest bridge: "I haven't built that; the closest I've done is X, and here's how I'd approach it." Confidence about a boundary beats a shaky bluff every time.

System design at scale

T014 JDs

Learn this: the standard scale-out story — stateless services behind a load balancer, a queue (Celery/Redis) for async work, caching layers, read replicas, sharding, and where each breaks. Learn to reason about the CAP trade-off and back-of-envelope QPS/latency.

Anchor: NFTRACE (Redis session isolation, two-tier storage) and the LLM Eval framework (Celery/Redis broker) — you already built the pieces; practice assembling them into a "scale to 10k req/min" narrative.

Recall check →

"Your LLM eval service gets 1000× traffic. Walk me from one Docker Compose box to a system that survives it." You must name: horizontal workers, broker back-pressure, DB connection pooling limits, and the first thing that falls over (the single Postgres).

The "how did you measure 70%?" answer

T0

Learn this: every headline number on your resume (70% auto-resolution, 55% MTTR, 50% validation time, ~60% cost cut) lacks a stated baseline in the reports. Interviewers will push. Prepare one honest methodology answer you reuse: what the baseline was, how you sampled, over what window.

Script: "We measured over [N weeks] against the pre-pipeline manual baseline of [X]. It's an internal operational metric, not a controlled study — directionally strong, and I can walk you through exactly how we counted an 'auto-resolved' error."

Recall check →

Say your measurement answer for the 5G pipeline's 70% out loud in under 20 seconds without inventing a fake A/B test. Honesty about method reads as senior; a made-up number reads as risk.

Own your self-disclosed gaps

T0

Learn this: three gaps hide in your projects and a sharp interviewer finds them. Pre-empt each and it becomes a maturity signal instead of a stumble: (a) EMS Postgres↔FAISS partial-write inconsistency, (b) Bias Auditor composite weights sum to 0.85 (length weight never applied), (c) no auth on EMS/NFTRACE despite sensitive data.

Turn it around: for (a) name the fix out loud — saga / outbox / compensating transaction. For (c) — "JWT + attribute-level RBAC, which I actually built at Brane." You already have the answer in a different project.

Recall check →

"What happens if the Postgres write succeeds but FAISS indexing fails?" Answer with the failure mode and the named pattern that fixes it. Don't say "that shouldn't happen."

Fine-tuning literacy (LoRA/PEFT)

T09 JDs

Learn this: the concepts — full fine-tune vs LoRA (freeze base, train low-rank adapters) vs PEFT vs QLoRA (quantized), and crucially when NOT to (most problems are prompt/RAG problems). Then do one tiny LoRA run on a small model with HuggingFace peft+trl so you can say "I've done it."

Anchor: your Ollama/qwen2.5 local-inference work + LLM-eval background means you already understand model params, temperature, and how to measure output quality — fine-tuning is the one missing verb.

Recall check →

"When would you fine-tune instead of RAG?" Strong answer: fine-tune for form/behaviour/format the model can't be prompted into reliably; RAG for knowledge. Name the cost: data curation + eval + drift, which is why you'd try prompt/RAG first.

Observability

T18 JDs

Learn this: the three pillars — logs, metrics, traces — and the tools (Prometheus scrape + Grafana dashboards + OpenTelemetry spans). For LLM apps specifically: token cost, latency p50/p95/p99, and eval-score-over-time as first-class metrics.

Do this: add a /metrics endpoint + a Grafana panel to your LLM Eval framework. One afternoon; converts a documented gap into a live demo.

Recall check →

"How would you know your RAG system degraded in production?" Name: latency + cost metrics, faithfulness-score trend, retrieval-hit-rate, and an alert threshold — tying straight back to what your eval framework already computes offline.

AWS refresh

T19 JDs

Learn this: the deploy-a-container path — ECS/Fargate or EKS, ALB, RDS (Postgres), ElastiCache (Redis), S3, and how IAM ties it together. You already know IAM/AppSync/AppFlow from Abjayon; you're refreshing, not learning from scratch.

Anchor: "I built GraphQL APIs on AppSync and managed IAM roles" — extend that to "here's how I'd deploy my FastAPI+Celery+Redis stack on ECS."

Recall check →

Sketch the AWS deployment of your LLM Eval stack (API + workers + Postgres + Redis) naming the service for each box. Where does the Bedrock-vs-self-hosted-model decision live?

CI/CD depth

T110 JDs

Learn this: a full pipeline — lint → test → build image → push → deploy → smoke test → rollback. Blue/green vs canary. Secrets handling. You've got real material: your Prompt Regression Suite is a CI gate, and Nokia NCD/TAF is genuine CD experience.

Anchor: "I built a GitHub Actions gate that blocks a merge when prompt quality regresses" is a standout CI story — most candidates only run unit tests. Lead with it.

Recall check →

"Design CI/CD for a service that ships a model." Include: eval gate before deploy, image build, staged rollout, and how you'd roll back a bad model version. Tie the eval-gate to your regression suite.

LangGraph

T15 JDs

Learn this: graph-based agent orchestration — nodes, edges, state, conditional routing, cycles for retry/verifier loops, checkpointing. You already hand-built this at Brane (agent loop, tool registry, retry-with-feedback verifier). LangGraph is just the named, standard version.

Anchor: "I built an agent loop with a verifier correction cycle by hand; here's how that maps to LangGraph's conditional edges and state graph" — turns a gap into a depth signal.

Recall check →

"Why a graph instead of a chain for agents?" Answer: chains are linear; agents need branching, loops (retry until verifier passes), and shared state — exactly the correction loop you built at Brane.

Project story bank

Interviewers don't grade your code, they grade your narration. For each flagship, rehearse two things: the Feynman line (explain it simply) and the depth hook (the one hard decision that proves seniority). Tick when you can deliver both smoothly.

5G Failure-Detection Pipeline flagship · telecom ▾

Feynman: "Network logs are huge and cryptic. My tool reads the packet capture, finds the error, looks up similar past errors in a smart database, and asks Claude to suggest the fix — turning hours of log-reading into seconds."

Depth hook: Qdrant over FAISS because it filters by vendor/layer at the DB level before similarity ranking — so a Nokia error never surfaces an Ericsson fix. That's a real correctness failure you designed out.

Watch: the 70%/55% numbers (use your measurement script); sentence-transformers is pip-installed but the shown code uses OpenAI embeddings — don't claim self-hosted embeddings; pcaps carry IMSI, so have a PII answer ready.

NFTRACE flagship · telecom ▾

Feynman: "Testing 5G means capturing traffic across many network boxes at once without them stepping on each other. I built a REST service that starts/stops/merges those captures, keeps each test run isolated in Redis, and validates the protocol flows automatically inside Nokia's CI."

Depth hook (your best impact story): a test could "pass execution but fail trace validation" — you decoupled assertion-level correctness from network-protocol correctness, catching a previously invisible bug class. That's an org-level workflow change, not a metric.

Watch: multiprocessing.Pool gives concurrent dispatch, not synchronized start — don't oversell "exact same instant"; the SIP rule snippet reads like a stub, so frame code excerpts as illustrative.

LLM Evaluation Framework differentiator ▾

Feynman: "AI models silently get worse when a vendor updates them. My system automatically grades AI answers four ways — including whether it stuck to the retrieved facts — and alerts the team before users notice."

Depth hook: faithfulness ≠ accuracy — high faithfulness + wrong answer means a retrieval problem; low faithfulness means context leakage. That diagnostic distinction is genuine eval-design nuance most people miss. Also: Celery over BackgroundTasks for CI-gate durability, and AND-logic (not averaged) pass/fail so a critical failure can't be masked.

Watch: "4 min vs 3 days" is from a simulated drift scenario — say so; no judge-calibration-against-humans yet (have the answer: spot-check a labelled set).

Bias & Fairness Auditor stats depth ▾

Feynman: "Change only the name on a prompt from Priya to James, run it hundreds of times, and measure if the AI treats them differently — with real statistics so it's signal, not noise — then produce a regulator-ready report."

Depth hook: ANOVA + Cohen's d (significance and effect size) because LLM output is stochastic; and a blind judge — demographics stripped before scoring so your bias detector isn't itself biased.

Watch (own it): composite weights sum to 0.85 — the length dimension (15%) is defined but never applied. If asked "do your weights sum to 1?", say plainly: "No — that's a real bug, partial rollout I didn't renormalize. Here's the one-line fix." Owning it cold is a maturity win.

EMS 2.0 & RF Keyword Generator RAG · hybrid-LLM ▾

EMS Feynman: "Drop a resume in, chat with your employee database in plain English. A local model extracts the data, three databases each store what they're best at, and vector search answers 'find a DevOps engineer' even when those words aren't on the resume."

RF-Gen depth hook (your cleanest design story): LLM only for what's unpredictable (natural language), deterministic templates for what's fixed (Robot Framework syntax), and the real RF parser as the validation gate — plus regex fallback for 100% uptime when the LLM fails. That "don't ask the LLM to do everything" instinct is exactly what senior AI hiring looks for.

Watch: EMS has no auth (PII!) — answer JWT+RBAC; the 4400-line main.py — have a "here's how I'd refactor into modules" answer; personal projects have no tests — acknowledge and contrast with your telecom 3-tier testing.

Landmine answers

Three questions can sink an otherwise strong interview because they cut across every project. Rehearse one honest answer for each — spoken, not just read.

📏

"How did you measure that?"

Every % is an internal operational metric vs a manual baseline, not a controlled study. Say that plainly and describe how you counted. Never invent an A/B test.

📈

"How does it scale?"

Your Celery/async/sharding scale-outs are designed, not built or load-tested. Say "proposed, not shipped" — then reason through it live. Pretending it's in prod is the trap.

🧪

"How did you test it?"

Telecom projects have real 3-tier testing — lead with those. Personal projects have none — acknowledge it and say what you'd add, don't bluff a test suite that isn't there.

Your unfair advantage: almost no AI-engineer candidate has real 5G-Core domain depth — AMF/AUSF, Diameter, NAS cause codes, 3GPP SBI endpoint names, Nokia NCD/TAF. It's hard to fake and impossible to cram. When a JD is telecom-adjacent, make it the spine of your pitch, not a footnote.
