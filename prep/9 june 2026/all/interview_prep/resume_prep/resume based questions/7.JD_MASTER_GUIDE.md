## 1.1 — Scalable RESTful backend APIs in FastAPI

> **JD:** "Design, build, and maintain scalable RESTful backend APIs using FastAPI and Python."

**What they're really checking:** can you build for *scale*, not just CRUD. Anyone can write a `@app.get`. They want to hear statelessness, structure, and worker model.

**Your answer (spoken):**
"The most complete FastAPI service I built end-to-end was NFTRACE at Nokia — a test lifecycle orchestration tool for 5G network-function testing. The core was a set of lifecycle endpoints — start a run, stop, merge parallel results, validate against a spec — each its own endpoint grouped under a lifecycle router. I structure large apps as one `APIRouter` per domain: lifecycle, session management, reporting, each in its own module, registered with a prefix. Shared resources — the Redis connection, the SQLite session, the XML-RPC SDK client — are wired as FastAPI dependencies through `Depends`, and I keep those dependencies small and composable, one concern each, so a route that needs Redis but not auth can declare just Redis.

The thing that makes it *scale*: the API is stateless. It holds nothing in memory. All session state lives in Redis, keyed `session:{uuid}` so each run is fully isolated, with SQLite for what needs to survive a flush. Stateless plus external state means horizontal scaling is just adding instances behind a load balancer — no sticky sessions. For serving it, I run Uvicorn workers under Gunicorn to use all cores, connection-pool the database, reuse the HTTP client, and paginate large list responses."

**3 sharpest points to land:** (1) router-per-domain + small composable `Depends`; (2) stateless handler + external state store = trivial horizontal scale; (3) Gunicorn+Uvicorn workers, connection pooling, pagination.

`→ Follow-up: "How many workers, and why?"` → "Rule of thumb is **2 × CPU cores + 1**. Then I measure — if workers are blocking on I/O more than CPU, I can add more; if they're CPU-saturated, more workers won't help and I'd reach for async or a queue instead."

## 1.4 — Contribute to architecture / system design

> **JD:** "Contribute to backend architecture and system design. / Collaborate on application architecture and contribute to backend system design."

**What they're really checking:** do you think in *trade-offs and failure modes*, or just name patterns.

**Your answer (spoken):**
"My design framework is a sequence: clarify the non-functional requirements and load, do a rough estimate, define the API, then the data model, then the architecture, then how it scales, then how it fails, and end on the trade-offs. The most significant call I made was on the 5G pipeline — where should LLM calls live: distributed, each component calling the model directly, or centralized behind one cache. I chose centralized. The reasoning: the LLM is expensive and slow, the same error patterns recur constantly, so distributed means duplicate calls at full latency. Result was **70% auto-resolution and a 55% cut in MTTR** — and that wasn't possible without the cache making repeat errors free. The senior signal is naming the cost: centralization buys control but introduces coupling; it's worth it when the thing you're centralizing is expensive and shared."

## 2.1 — Third-party service integration

> **JD:** "Integrate backend services with: ... Third-party services."

**What they're really checking:** have you made an *unreliable* dependency reliable?

**Your answer (spoken):**
"My playbook for any external call is four layers. One — an explicit timeout matched to the service's SLA, never the library default, which is often infinite. Two — retry with exponential backoff: 1s, 2s, 4s, capped at three, **with jitter** so a fleet of clients doesn't all retry on the same tick and create a thundering herd. I name `tenacity` for this. Three — a circuit breaker: if more than half the calls fail in a 60-second window, stop calling and return the fallback immediately, so a dead dependency can't tie up my whole pipeline in timeouts. Four — the fallback itself, which is the part people skip. On the RF Keyword Generator the fallback was deterministic templates then regex, and it gave us 100% feature uptime through a real provider outage. I also cache hot reads to cut dependency volume outright.

For webhooks specifically, four rules: validate the HMAC signature before processing, respond 200 fast to acknowledge, do the real work asynchronously, and deduplicate on the event ID because senders retry — I store seen IDs in Redis with a TTL."

**Sharpest points:** timeout → retry+backoff+**jitter** (`tenacity`) → circuit breaker → degraded fallback; cache to cut volume; webhook 4 rules (signature, 202-fast, async, idempotency).

`→ Follow-up: "Why jitter?"` → "Without it, all clients that failed at the same moment retry at the same moment — a synchronized stampede that re-overloads the recovering service. Jitter randomizes the retry delay so the load spreads out."

## 2.2 — Authentication (JWT / OAuth)

> **JD:** "Able to Handle: Authentication (JWT/OAuth)."

**What they're really checking:** production scars, not documentation knowledge.

**Your answer (spoken):**
"In NFTRACE the model was HS256-signed JWT access tokens, 15-minute expiry, sent as a Bearer token; `OAuth2PasswordBearer` defines the scheme and a `get_current_user` dependency validates the signature with python-jose and returns the user — any route declaring that dependency is protected. The scar I always mention: **a JWT is signed, not encrypted.** The signature proves nobody tampered with it, but the payload is just base64 JSON — anyone decodes it in DevTools in two seconds. A developer put a user attribute that was borderline-PII in the payload 'to save a database call'; we caught it in review. The rule I enforce: only put in the payload what you'd be fine seeing on a screen — user ID, role, expiry, JTI (JWT ID — unique token identifier). Nothing else.

On OAuth2, the common web flow is authorization-code: redirect to the auth server, user consents, you get a code, you exchange the code for a token — and **PKCE** (Proof Key for Code Exchange — prevents authorization code interception attacks) protects that exchange for public clients. For revocation, since JWTs are stateless, I keep a Redis blacklist on the **JTI** claim with a TTL equal to the token's remaining life, checked after signature validation. And **HS256 vs RS256**: HS256 shares one secret, fine for a single service; the moment you have multiple services you want RS256 — the auth server signs with a private key and everyone else verifies with the public key, so no other service can mint tokens. Passwords are bcrypt or argon2, never stored plaintext."

`→ Follow-up: "How do you log a user out with JWTs?"` → "Not by 'deleting it on the client' — that's the ⚠️ weak answer; the token is still valid until expiry. You add its **JTI to a Redis blacklist** with a TTL of the remaining lifetime and reject blacklisted JTIs on every request. Short expiry plus blacklist."

## 2.3 — Error handling & validation

> **JD:** "Able to Handle: ... Error handling and validation."

**What they're really checking:** do your errors serve the frontend as a *contract*?

**Your answer (spoken):**
"NFTRACE started with the FastAPI default — `{"detail": "..."}` — and the SDK team couldn't tell a session-not-found from a malformed input; both were an unstructured string they had to string-match on, which breaks the moment you reword a message. **Sharpest points:** RFC 7807 + machine-readable `code` (the NFTRACE retrofit); Pydantic 422 for free; separate input vs domain models to block mass-assignment / privilege escalation; never leak internals.

## 3.1 — How React/Next.js actually consumes your API

> **JD:** "Understand API consumption patterns from frontend."

**What they're really checking:** do you know what's on the other side of your endpoint, or do you just throw JSON over the wall?

**Your answer (spoken):**
"Modern React rarely calls raw `fetch` in a component. It uses **React Query — TanStack Query — or SWR**: libraries that wrap your endpoint in a cache keyed by a 'query key,' handle loading and error states, deduplicate concurrent requests for the same key, and **refetch on window focus or reconnect**. Why I care as the backend: they cache by key and expect a **stable response shape** for that key. If `GET /jobs/{id}` sometimes returns `result: null` and sometimes omits `result` entirely, their cache and their TypeScript types break. Shape stability is a contract, not a nicety.

**Next.js App Router** splits fetching in two. **Server Components** — `async` components — fetch on the Next.js server: no CORS, because the request originates server-side, and Next extends `fetch` with its own caching, like `fetch(url, { next: { revalidate: 60 } })`. **Client Components** — marked `"use client"` — fetch in the browser, so CORS applies. So 'the frontend is calling you' is sometimes the browser and sometimes the Next.js server, and those have *different* CORS and auth behavior.

And there's the **BFF pattern** (Backend-for-Frontend — a server-side layer that calls the API on behalf of the browser): Next.js **Route Handlers** — `app/api/.../route.ts` — often sit between the browser and my API as a backend-for-frontend. The browser calls Next, Next calls me server-to-server. That's why a frontend dev might say 'there's no CORS issue on our side' — because the browser never hits my API directly; their Next server does."

`→ Follow-up: "If they use Server Components, do you still need CORS configured?"` → "For the Server-Component and BFF paths, no — those are server-to-server, same-origin from the browser's view. But the moment any Client Component calls me directly from the browser, CORS applies. I configure it correctly regardless, because mixed setups are normal."

## 3.2 — Where the JWT lives (and why it's YOUR problem)

> **JD:** "Work closely with frontend teams (React/Next.js)." (auth-handling dimension)

**What they're really checking:** do you understand that a *frontend* storage choice forces *backend* config — and that you decide it together.

**Your answer (spoken):**
"There are three places the token can live, each a trade-off. **localStorage** — survives reload, dead simple, but it's readable by any injected script, so it's XSS-exposed. **In-memory** — XSS-safer, but lost on reload, so it needs a silent refresh flow. **httpOnly cookie** — JavaScript can't read it, so XSS can't steal it, but now you're CSRF-exposed, so you need `SameSite` and sometimes a CSRF token. The modern Next.js answer is usually a refresh token in an **httpOnly, Secure, SameSite cookie** with a short-lived access token in memory — or the **BFF pattern where the tokens live server-side in the Next session and the browser never sees a token at all**.

Here's why it's my problem as the backend: **if they use cookies, my CORS must set `allow_credentials=True`, the frontend must send `credentials: 'include'`, and I cannot use `allow_origins=['*']`** — that combination is illegal and the browser rejects it. And if the API and frontend are on different domains, the cookie needs `SameSite=None; Secure` or it won't be sent at all. Those are backend config decisions driven entirely by a frontend storage choice — so it's a conversation we have together, not something either side decides alone."

`→ Follow-up: "Why is '*' plus credentials illegal?"` → "Because it would let *any* website on the internet make authenticated, cookie-bearing requests to your API on the user's behalf. The spec forbids the combination; the browser silently drops the response. You must name explicit origins when credentials are involved."

## 3.3 — CORS: the real mechanics (the #1 frontend-backend friction point)

> **JD:** "Support/debug API issues impacting UI." (CORS dimension)

**What they're really checking:** can you debug the single most common browser-vs-backend dispute without flailing.

**Your answer (spoken):**
"The browser enforces same-origin policy, so cross-origin calls trigger CORS. **Simple requests** — a GET or POST with simple headers — just need `Access-Control-Allow-Origin` on the response. **Non-simple requests** — a custom header like `Authorization`, a method like PUT or DELETE, or `Content-Type: application/json` — trigger a **preflight `OPTIONS`** first. My API has to answer that OPTIONS with `Allow-Origin`, `Allow-Methods`, `Allow-Headers`, and for cookies `Allow-Credentials`, before the browser will even send the real request.

Three classic failures. One — `allow_origins=['*']` *with* `allow_credentials=True`: invalid combo, browser rejects it. Two — forgetting `Authorization` in `allow_headers`: the preflight passes for simple calls but the real authenticated request is blocked, which shows up as 'auth randomly fails.' Three — no `Access-Control-Max-Age`: the OPTIONS fires on *every* request and adds latency.

The line I say out loud: **a CORS error in the browser console is almost always a server-side config issue, not a frontend bug. The giveaway is 'works in Postman, fails in the browser' — Postman doesn't enforce CORS, browsers do. So when a frontend dev reports it, I check my CORS middleware first.** I've actually lived this — the SDK team reported a 'connection error' that never appeared in our server logs, because a CORS preflight rejection happens at the browser before the request reaches the server. The fix was adding their `localhost:3001` dev origin to the allow-list."

`→ Follow-up: "Why does a CORS failure not show in your server logs?"` → "The browser rejects the response *after* the preflight, or refuses to send the real request at all — so from the server's side either nothing arrives or only an OPTIONS does. You debug it in the browser's Network tab, not the server log. That's the tell."

## 3.4 — Smooth data exchange: the contract details that cause friction

> **JD:** "Ensure smooth data exchange and endpoint design."

**What they're really checking:** have you thought past the demo to the details that actually break integrations.

**Your answer (spoken — keep every specific):**
"There are six contract details I get right up front because each one is a real source of friction:

- **Casing** — backend snake_case versus frontend camelCase. Decide once: either emit camelCase via a Pydantic alias generator, or document that the frontend maps it. The sin is being inconsistent across endpoints.
- **Dates** — always ISO 8601 UTC strings, like `2026-06-22T09:00:00Z`. Never mix epoch integers and strings, because the frontend feeds these straight into date-fns or dayjs.
- **Null vs missing** — pick one. A field that's sometimes `null` and sometimes absent breaks JS destructuring and TS types in different ways. I use `response_model` with explicit defaults so the shape is invariant.
- **Enums as strings**, not magic ints — the frontend switches on `"status": "processing"`, not on `2`.
- **Pagination shape** — infinite-scroll UIs using React Query's `useInfiniteQuery` want a **stable cursor plus a `hasMore` flag**. Offset/limit breaks during infinite scroll: if rows get inserted or deleted between page fetches, items duplicate or vanish. Cursor pagination is stable under change.
- **Error envelope** — one consistent shape, `{error:{code,message}}` or RFC 7807, so the frontend writes **one** axios interceptor or React Query `onError` handler instead of a special case per endpoint."

`→ Follow-up: "Cursor vs offset — convince me."` → "Offset says 'skip 40, take 20.' If three rows are deleted above the window between fetches, page 3 now starts three rows earlier and the user sees duplicates; inserts cause skips. A cursor says 'give me the 20 after *this* item' — it's anchored to a stable row, so concurrent inserts and deletes don't corrupt the sequence. For a feed that's changing while you scroll, cursor is the correct choice."

## 4.1 — Write and understand SQL queries

> **JD:** "Write and understand SQL queries (joins, aggregations, filters)."

**What they're really checking:** this is very likely a **live query**. They want to watch you think.

**Your answer (spoken) + how to perform it:**
"The one rule that unlocks most queries is **logical execution order**: `FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT`. That's why WHERE filters rows before grouping, HAVING filters groups after, and you can't use a SELECT alias in WHERE. When I write live, I narrate: I state the goal in plain English, name the pattern, then write clause by clause saying what each does.

The five patterns I make sure I can write cold: **Nth-highest-per-group** with a window function — `DENSE_RANK() OVER (PARTITION BY ... ORDER BY ... DESC)` in a subquery, then filter the rank. **Anti-join** — `LEFT JOIN ... WHERE right.id IS NULL` to find rows with no related record. **Duplicates** — `GROUP BY col HAVING COUNT(*) > 1`. **Top-N-per-group** — rank in a subquery, filter `rn <= N`. And **count including zeros** — `LEFT JOIN` then `COUNT(child.id)` not `COUNT(*)`, so users with no orders correctly get 0, not 1."

⚠️ **Weak-answer trap:** writing the query silently. The interviewer is scoring *how* you think — narration saves you even if syntax slips.

`→ Follow-up: "Why DENSE_RANK and not RANK for Nth-highest?"` → "RANK skips numbers on ties — two people tie for first, both are rank 1, nobody is rank 2, so filtering rank 2 returns nothing. DENSE_RANK never skips, so the second-highest is always there."

## 4.2 — Schema design

> **JD:** "Design and maintain relational database schemas using SQL (PostgreSQL/MySQL/SQL Server)."

**What they're really checking:** have you designed schemas under *real constraints*, or only drawn ER diagrams.

**Your answer (spoken):**
"The most complex schema I designed was Brane's multi-agent execution model. Multiple AI agents process the same content artifact — a 'learning object' — and each run needs its own isolated input, scratch space, and episode log. So: `learning_objects` for the artifact; `lo_input_execution_agent` as the junction table linking learning objects to agents with execution metadata; `agent_run_scratch` for mutable per-run workspace; and `agent_episodes` as an append-only immutable log. Plus an RBAC layer alongside.

The hard lesson — and the design trap — was where execution state goes. My first version put run state directly on the junction table: `current_status`, `last_checkpoint`, scratch data as columns. That broke the moment we needed multiple concurrent runs for the same agent-LO pair, because a junction table is a *relationship* — you get one row per pair. So I moved mutable state to sibling tables linked by a `run_id`. The principle: **a junction table models a relationship and carries relationship metadata; mutable and per-instance state belongs in dedicated execution tables.** My deepest hands-on is PostgreSQL, but the fundamentals — keys, normalization, constraints — transfer directly to MySQL and SQL Server with minor syntax differences."

**Sharpest points:** Brane junction + sibling execution tables; junction-models-relationship-not-mutable-state; deliberate denormalization as a read-perf vs consistency trade-off; Postgres-deep, fundamentals transfer.

`→ Follow-up: "When would you deliberately denormalize?"` → "When a read is hot and the join cost is hurting it, and the duplicated data changes rarely. You're trading write-time consistency work for read speed — acceptable when reads vastly outnumber writes and you control all the write paths."

## 4.3 — Data accuracy, consistency, integrity

> **JD:** "Ensure data accuracy, consistency, and integrity across systems."

**What they're really checking:** do you know constraints are a *safety net*, not the primary strategy.

**Your answer (spoken):**
"On Brane's RBAC tables, `permissions` references `subjects`, `resources`, and `attributes` by foreign key. Without integrity constraints you get orphaned permissions pointing at deleted resources — or worse, granting access to a resource ID that later gets reassigned. So I used FK constraints deliberately: **`ON DELETE CASCADE` for cleanup dependencies** — delete a resource and its permissions go with it — and **`ON DELETE RESTRICT` for protection** — an agent with active runs can't be deleted, the database refuses. ACID is the backstop: atomicity so a multi-step write is all-or-nothing, isolation so concurrent transactions don't corrupt each other. The scar: an early cascade was too aggressive — deleting a workspace cascaded all the way to authentication records, which was wrong; a user losing one workspace shouldn't lose their auth. I had to untangle the chain and add explicit RESTRICT. The principle I hold: **application logic enforces the rule before the DB; the FK constraint is the last-resort guarantee for when app logic is bypassed.**"

`→ Follow-up: "CASCADE or RESTRICT by default?"` → "RESTRICT by default — it fails loudly and forces you to think about the dependency. CASCADE only where the child genuinely has no meaning without the parent, like permissions without their resource. An over-eager CASCADE silently deletes data you didn't mean to."

## 4.4 — Troubleshoot database issues

> **JD:** "Troubleshoot and support database-related issues."

**What they're really checking:** a repeatable *process*, not luck.

**Your answer (spoken):**
"Two real ones. **N+1** in NFTRACE's session-list endpoint: fetch all sessions, then one query per session for its last run — 50 sessions meant 51 round-trips. I found it by adding **query-logging middleware** in dev; seeing 51 queries fire for one page load made it obvious. Fix was a single **LEFT JOIN** — and LEFT, not INNER, so sessions with no runs still appear. The lesson: N+1 is invisible reading the code, it looks like two innocent lines; you have to *measure* query counts.

**Slow query**: a status filter taking 2–3 seconds on ~10k rows. Process — capture the actual SQL, run **`EXPLAIN ANALYZE`** (or `EXPLAIN QUERY PLAN` in SQLite), see a **Seq Scan**, realize the column had no index, add the index, re-run EXPLAIN to confirm an index scan, verify the timing dropped — it went to under 20ms. And the trap I always name: a filter like **`WHERE DATE(created_at) = '2026-01-01'` wraps the column in a function and defeats the B-tree index** — the fix is a range, `>= '2026-01-01' AND < '2026-01-02'`, which is index-friendly. Indexes aren't free — every index is a write penalty, so I index what I filter, join, or sort on, and no more."

`→ Follow-up: "How do you read EXPLAIN ANALYZE output?"` → "I look for `Seq Scan` on a large table — that's the red flag, no index used. `Index Scan` means it's working. And I compare actual rows to estimated rows — a big gap means stale statistics, so I run `ANALYZE` to refresh them."

# DEEP DIVE: Microservices

> Supports JD line **1.2** ("microservices-based architecture"). study_guide/06_System_Design_Microservices.md already covers monolith-vs-micro, communication styles, saga, outbox, and decomposition — **point there for those.** This section adds the three things that file doesn't: your real microservice told properly, inter-service authentication, and the honest scope frame.

## D1 — Your real microservice: the gRPC model gateway

**What they're really checking:** do you have a genuine service story, or are you calling a module a "microservice."

**Your answer (spoken):**
"At Brane I built the gRPC model gateway, and it's a genuine microservice, not a module. It was a separate service for concrete reasons: its **scaling profile was different** from the application API — model calls are heavy and slow, the app API is light and fast, so they needed to scale independently; its **deploy cadence was different** — provider-routing logic changed often without touching the app; and it **isolated a concern** — multi-provider routing across instruct, thinking, and vision models behind one typed contract. I made it **stateless** — no session state in memory, all routing config and provider health in PostgreSQL — so horizontal scaling was just adding instances behind a load balancer. The early mistake was an **in-memory connection pool per instance**, which multiplied connections and hit provider limits at three-plus instances; I moved connection management to per-request setup with reuse at the provider-client level. I chose **gRPC over REST** because it's internal, high-throughput, strongly typed via protobuf, runs on HTTP/2, and supports **deadline propagation** — the caller's timeout flows through to the gateway, so a slow provider can't outlive the request that wanted it."

`→ Follow-up: "What made it earn being a separate service rather than a module?"` → "Three of my four split criteria were met at once: different scaling profile, different deploy cadence, and a cleanly isolated concern. If only one had been true I'd have kept it as a module in the monolith — one reason usually isn't enough to pay the distributed-systems tax."

## D2 — Inter-service authentication (the topic interviews probe and most candidates miss)

**What they're really checking:** once services talk to each other, how does service A *trust* service B.

**Your answer (spoken):**
"Three approaches, increasing in rigor:

- **Network trust / mTLS** — services live in a private network, and mutual TLS means each side presents a certificate, so both authenticate each other at the transport layer. This is common in a service mesh like Istio or Linkerd, where the mesh injects the certs.
- **Service tokens via OAuth2 client-credentials** — the machine-to-machine flow: service A presents its own `client_id` and `client_secret` to an auth server, gets a short-lived access token, and sends it to B. No user is involved.
- **RS256 JWT with public-key verification** — the auth service signs tokens with a **private** key and every other service verifies with the **public** key. The win is that no service except the issuer holds the signing secret, so a compromised service can't *mint* tokens, only verify them. That's exactly why RS256 beats HS256 once you have more than one service: with HS256's shared secret, every service that can verify can also forge."

`→ Follow-up: "Why RS256 over HS256 between services specifically?"` → "HS256 uses one shared secret for both signing and verifying, so every service holding it to *verify* tokens can also *forge* them — one breach compromises the whole mesh. RS256 splits them: only the issuer has the private signing key; everyone else gets the public key and can verify but never mint. Asymmetric keys are the right call the moment more than one service is in play."

## D3 — The honest scope frame

> 💀 **Say this if they probe scale. It converts a gap into senior judgment.**

"I'll be straight about scope: my microservices experience is the gRPC model gateway plus designing service decomposition — not running a 50-service mesh. But I think that's the right instinct anyway. My rule is start with a well-structured modular monolith and extract a service only when there's a concrete reason — a different scaling profile, a different deploy cadence, separate team ownership, or a compliance boundary. The gateway met that bar — heavy, slow, independently scaled — so it earned being its own service. I've seen the alternative: teams that went microservices-first and spent six months on service-mesh and tracing infrastructure instead of shipping. Senior judgment here is knowing when *not* to split."
