API CONTRACT & FRONTEND DATA EXCHANGE (JD: "smooth data exchange and endpoint design")
├── Casing — snake_case (backend) vs camelCase (frontend); decide once, use Pydantic alias generator
├── Dates — always ISO 8601 UTC strings (2026-06-22T09:00:00Z); never mix epoch ints + strings
├── Null vs missing — pick one; use response_model defaults for invariant shape
├── Enums as strings — "status": "processing" not "status": 2
├── Cursor vs offset pagination — cursor stable under inserts/deletes; offset breaks infinite scroll
├── Error envelope — one consistent shape ({error:{code,message}}) = one onError handler for frontend
└── Versioning — /v1/ prefix; never remove a field in same version; add then deprecate

RATE LIMITING (JD: "API performance and scalability")
├── Why — prevent abuse, enforce per-user quotas, protect expensive endpoints (AI generation)
├── Two layers — IP-level at gateway (DDoS protection) + per-user in app (business quotas)
├── Redis sliding window — INCR + EXPIRE per user/window key
├── Response — 429 Too Many Requests + Retry-After header
└── Your anchor — Brane: generation endpoint rate-limited per user tier (free vs pro)

DEPLOYMENT STRATEGIES (DevOps depth beyond CI/CD)
├── Rolling — update instances one by one; zero downtime but mixed-version window
├── Blue-green — two environments, switch traffic; instant rollback, double infra cost
├── Canary — small % of traffic to new version; catch issues before full rollout
├── Your anchor — Nokia zero missed deliveries; GitLab pipeline with manual approval gate
└── Rollback decision — on error rate spike post-deploy, rollback is faster than hotfix

OBSERVABILITY (RED method + more)
├── RED metrics — Rate (req/sec), Errors (error rate %), Duration (p50/p95/p99 latency)
├── Structured logging — JSON, always include: request_id, user_id, endpoint, latency_ms, status_code
├── Distributed tracing — trace_id propagates from HTTP request → queue message → worker log
├── Health check endpoints — /health (liveness: am I alive?) vs /ready (readiness: can I take traffic?)
├── Alert on symptoms not noise — error rate >1%, p99 >2× baseline, DLQ depth >50, queue depth >2000
└── What to never log — secrets, tokens, passwords, PII

IDEMPOTENCY (cross-cutting concept — appears in webhooks, retries, payments)
├── Definition — calling the same operation twice = same result as calling once
├── Why it matters — retries are safe only if idempotent; network can deliver twice
├── Implementation — idempotency key in request header; store processed key in Redis with TTL
├── Your anchors — webhook dedup (setnx event_id), Celery task_acks_late, job_id UUID for generation
└── Non-idempotent danger — charge twice, send two emails, create two records

CAP THEOREM (system design depth signal)
├── Consistency — every read sees the latest write
├── Availability — every request gets a response (may be stale)
├── Partition tolerance — system works despite network splits (always assumed in distributed systems)
├── In practice — choose CP (banks, strong consistency) or AP (most web apps, eventual consistency)
└── Your systems — 5G pipeline = AP (eventual); Brane RBAC = CP (permissions must be current)

CONNECTION POOLING (performance depth signal)
├── Why — opening a DB connection is expensive (~50ms); pool reuses them
├── SQLAlchemy pool — pool_size (persistent), max_overflow (burst), pool_timeout (wait limit)
├── FastAPI pattern — create engine once at startup, use get_db() Depends per request
├── Danger — pool exhaustion: too many concurrent requests, workers starve waiting for a connection
└── Your anchor — NFTRACE SQLite (single-writer, pool size 1); Brane PostgreSQL (pool_size=10)
