# SQL — Questions WITH Worked Solutions

SQL is the highest-risk part because they may make you **write a query live.** For each one: try to write it yourself first (cover the solution), then check. Do all of them Friday. Each has the answer *and the explanation* so you learn the pattern, not just the answer.

**The one rule that unlocks most of these — logical execution order:**
`FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT`
(That's why WHERE filters rows *before* grouping, HAVING filters *after*, and you can't use a SELECT alias in WHERE.)

---

## How to Narrate While Writing SQL (more important than the answer itself)

**Before you write a single character:**
1. "So I need to find [state the goal in plain English]."
2. "The pattern here is [name it: anti-join / window rank / running total / GROUP BY filter]."
3. "My approach: [one sentence]."

**While writing, say what each clause does:**
- "FROM orders — that's my base table."
- "LEFT JOIN users — I want all orders even if there's no user."
- "PARTITION BY department — this ranks within each department separately."
- "HAVING not WHERE — because I'm filtering on the aggregate after grouping."

**If you make a mistake:**
"Actually — let me reconsider that." [Fix it out loud.] "There we go — that's cleaner."

The interviewer is scoring HOW you think, not just the final SQL. Narration saves you even if the syntax isn't perfect.

**If you're stuck:** "Let me think about what I need..." then think out loud. "I need all users — so LEFT JOIN preserves them. I want the ones with no match — so I filter for NULL on the joined side." Work through the logic first, SQL second.

### 1. Find the 2nd highest salary (whole company)
```sql
SELECT MAX(salary) AS second_highest
FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);
```
**Why:** the subquery finds the top salary; the outer query finds the biggest salary *below* it. Simple and robust.

---

### 2. Find the Nth highest salary *per department* (window function)
```sql
SELECT name, department, salary
FROM (
  SELECT name, department, salary,
         DENSE_RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS rnk
  FROM employees
) ranked
WHERE rnk = 2;          -- change 2 to N
```
**Why:** `DENSE_RANK() OVER (PARTITION BY department ORDER BY salary DESC)` ranks salaries *within each department*, highest first. Wrap it in a subquery, then filter to the rank you want. Use `DENSE_RANK` so ties don't skip numbers.

---

### 3. Find all users who have NO orders (anti-join)
```sql
SELECT u.id, u.name
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;
```
**Why:** a LEFT JOIN keeps every user; users with no orders get NULLs on the order columns. Filtering `WHERE o.id IS NULL` keeps exactly those. This "LEFT JOIN + IS NULL" is *the* anti-join pattern — memorize it.

---

### 4. Find duplicate emails
```sql
SELECT email, COUNT(*) AS cnt
FROM users
GROUP BY email
HAVING COUNT(*) > 1;
```
**Why:** group by the column, count per group, and HAVING keeps only groups with more than one — i.e. duplicates. (WHERE can't do this because the count doesn't exist until after grouping.)

---

### 5. Total revenue per customer, only customers over 1000, highest first
```sql
SELECT customer_id, SUM(amount) AS total
FROM orders
WHERE status = 'paid'
GROUP BY customer_id
HAVING SUM(amount) > 1000
ORDER BY total DESC;
```
**Why:** this is the full pipeline — WHERE filters rows first, GROUP BY aggregates per customer, HAVING filters the totals, ORDER BY sorts. A great one to talk through out loud to show you understand execution order.

---

### 6. Top 3 products by revenue within each category (window + ranking)
```sql
SELECT category, name, revenue
FROM (
  SELECT p.category, p.name,
         SUM(oi.quantity * oi.price) AS revenue,
         ROW_NUMBER() OVER (PARTITION BY p.category
                            ORDER BY SUM(oi.quantity * oi.price) DESC) AS rn
  FROM products p
  JOIN order_items oi ON oi.product_id = p.id
  GROUP BY p.category, p.name
) ranked
WHERE rn <= 3;
```
**Why:** aggregate revenue per product, rank within each category with `ROW_NUMBER() OVER (PARTITION BY category ORDER BY revenue DESC)`, then keep the top 3. "Top N per group" is a classic — the pattern is always *rank in a subquery, then filter*.

---

### 7. Running monthly revenue total (window, running sum)
```sql
SELECT month,
       SUM(amount) OVER (ORDER BY month) AS running_total
FROM monthly_revenue
ORDER BY month;
```
**Why:** `SUM(...) OVER (ORDER BY month)` computes a cumulative total row by row, without collapsing rows the way GROUP BY would. This is what window functions are *for* — calculations across rows while keeping every row.

---

### 8. Join three tables with a filter (the everyday query)
```sql
SELECT u.name, p.name AS product, oi.quantity
FROM users u
JOIN orders o      ON o.user_id = u.id
JOIN order_items oi ON oi.order_id = o.id
JOIN products p     ON p.id = oi.product_id
WHERE o.created_at >= '2026-01-01';
```
**Why:** chain JOINs through the foreign keys connecting the tables, then filter. Be comfortable joining 3+ tables fluently — this is the bread-and-butter of backend SQL.

---

### 9. Count orders per user, *including* users with zero (LEFT JOIN + aggregate)
```sql
SELECT u.name, COUNT(o.id) AS order_count
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.name
ORDER BY order_count DESC;
```
**Why:** the LEFT JOIN keeps all users; `COUNT(o.id)` counts non-NULL order ids, so users with no orders correctly get 0 (not 1). Note: `COUNT(o.id)` not `COUNT(*)`, because `COUNT(*)` would count the NULL row as 1.

---

### 10. Second-highest using a window (alternative to #1)
```sql
SELECT DISTINCT salary
FROM (
  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
  FROM employees
) t
WHERE rnk = 2;
```
**Why:** good to know two ways. If they ask "what if there are ties?" the `DENSE_RANK` version handles that cleanly.

---

### 11. Delete duplicate rows (keep one per email)
```sql
DELETE FROM users
WHERE id NOT IN (
  SELECT MIN(id)
  FROM users
  GROUP BY email
);
```
**Narration for this:** "I need to keep exactly one row per email — the one with the lowest ID. So I find the MIN id per email group, and delete everything NOT in that set."
**Why:** Group by the duplicate column, keep the minimum ID (the "original"), delete everything else. This is the safe pattern — it never deletes the last copy.
`→ Follow-up: "What if there are NULLs in the email column?" — NULL != NULL in SQL, so NULLs would never match and would all be deleted. Add WHERE email IS NOT NULL to protect them, or handle separately.`

---

### 12. Customers active in ALL three months of a quarter
```sql
SELECT customer_id
FROM orders
WHERE order_date >= '2026-01-01' AND order_date < '2026-04-01'
GROUP BY customer_id
HAVING COUNT(DISTINCT DATE_TRUNC('month', order_date)) = 3;
```
**Narration:** "I need customers who ordered in every month. DATE_TRUNC normalizes dates to month-level, COUNT DISTINCT counts unique months, HAVING = 3 means all three are present."
**Why:** Classic "every X" pattern — count the distinct values and filter where the count equals the total you need.

---

### 13. Snowflake-specific — QUALIFY (rank and filter in one step)
```sql
-- Standard SQL (works everywhere):
SELECT name, department, salary FROM (
  SELECT name, department, salary,
         ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) rn
  FROM employees
) t WHERE rn = 1;

-- Snowflake shortcut with QUALIFY:
SELECT name, department, salary
FROM employees
QUALIFY ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) = 1;
```
**Why this matters:** QUALIFY is Snowflake-specific — it lets you filter on window functions directly without a subquery. Knowing this signals real Snowflake awareness beyond the basics. Mention it if they ask about Snowflake-specific features.

## ⚠️ Questions Designed to Catch AI-Copy-Paste SQL

These are follow-ups interviewers use when they think you wrote the query without understanding it. Practice saying each answer out loud.

**"Why DENSE_RANK and not RANK for the Nth-highest salary?"**
"RANK skips numbers on ties — if two people tie for first, they're both rank 1 and nobody is rank 2, so filtering for rank 2 returns nothing. DENSE_RANK never skips — ties get the same rank and the next value is always next. For 'find the 2nd highest,' DENSE_RANK is almost always what you actually want."

**"In the anti-join, why filter on `o.id IS NULL` and not `o.user_id IS NULL`?"**
"o.id is the primary key — it's only NULL when there's no matching row from the LEFT JOIN, which is exactly what I'm testing for. o.user_id could theoretically be NULL for other data reasons. Filtering on the PK is the cleanest, most explicit way to say 'no match existed.'"

**"Why does COUNT(o.id) give 0 for users with no orders, but COUNT(*) gives 1?"**
"COUNT(column) skips NULLs. COUNT(*) counts every row including the NULL placeholder row the LEFT JOIN creates for unmatched users. So COUNT(*) would tell you that every user placed exactly 1 order, which is completely wrong. You have to use COUNT(o.id) to count actual order records."

**"Would an index on created_at be used by WHERE DATE(created_at) = '2026-01-01'?"**
"No — wrapping the column in a function defeats the B-tree index. The database can't use the index to find DATE(created_at) = X because the index stores the raw value, not the result of the function. The fix is to expand the filter to a range: WHERE created_at >= '2026-01-01' AND created_at < '2026-01-02'. Same logical result, index-friendly."

**"What's the difference between EXISTS and IN for a subquery filter?"**
"EXISTS short-circuits — as soon as it finds one matching row, it stops. IN evaluates the entire subquery result set first. For large subqueries, EXISTS is usually faster. There's also a correctness difference: if the subquery returns any NULLs, IN can behave unexpectedly — NOT IN with a NULL in the set returns no rows at all, which is a famous SQL gotcha. EXISTS handles NULLs correctly."

# Window functions vs GROUP BY — be ready to explain this
"GROUP BY collapses rows into one row per group — you lose the individual rows. A window function calculates across a set of rows but *keeps every row* — so you can show each employee alongside their department's average, or compute a running total. That's the key difference: GROUP BY aggregates and collapses; window functions aggregate without collapsing."

# If they ask you to optimize a query
Walk this out loud: "First I'd run EXPLAIN ANALYZE to see the plan. If it's doing a full table scan on a filtered or joined column, I'd add an index there. I'd check for an N+1 pattern in the application code. And if it's a heavy read that runs often, I'd consider caching the result."
