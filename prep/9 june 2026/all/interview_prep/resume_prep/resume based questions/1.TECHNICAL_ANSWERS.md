# SECTION 1 — FastAPI

**Q1. What is FastAPI and why would you use it?**
"FastAPI is a modern Python web framework for building APIs. The three reasons I reach for it: first, it's async-native, built on ASGI, so it handles lots of concurrent I/O — like database calls or calls to other services — very efficiently. Second, it uses Pydantic, so request and response data is validated automatically against typed models — fewer bugs, less boilerplate. And third, it auto-generates interactive API documentation, Swagger, which makes it really easy to collaborate with frontend teams because they get a live contract to work against."

To understand how **ASGI (Asynchronous Server Gateway Interface)** handles high concurrent I/O, it is helpful to compare it to the traditional **WSGI (Web Server Gateway Interface)** model.

---

### 1. The WSGI Model: One Thread per Request (Synchronous)
In traditional Python web frameworks (like Django or Flask running on WSGI servers like Gunicorn):
* **How it works:** Every incoming HTTP request is assigned to a single thread or process. 
* **The I/O bottleneck:** If a request needs to fetch data from a database or call an external API, the thread stops and waits (**blocks**) for the database/API to respond.
* **Concurrency limit:** During this wait time, the thread cannot do anything else. If you have 20 worker threads, your server can only handle 20 concurrent requests. To handle more, you have to spin up more threads/processes, which consumes a significant amount of system memory and CPU.

"Bolt-on" means the feature wasn't designed in from the start — it was added later, as an afterthought, on top of an existing system that wasn't built for it.

Flask and Django were built on WSGI, which is fundamentally synchronous. When async Python became popular, they added async support in later versions — but it's patchy and incomplete because the core architecture wasn't designed for it. You can write async def in Flask/Django, but:

The underlying server gateway (WSGI) still handles requests synchronously
Many built-in parts (ORMs, middleware, session handling) don't support async
You don't get the real concurrency benefits you'd expect
It's like adding a turbocharger to a car engine that wasn't designed for one — it technically works, but it's not clean, and you're fighting the original design.

FastAPI, by contrast, was built on ASGI from day one — async isn't added on, it's the foundation the whole thing runs on.

---

### 2. The ASGI Model: The Event Loop (Asynchronous)
ASGI (used by frameworks like FastAPI, Starlette, or Channels running on servers like Uvicorn or Daphne) is built on Python's `asyncio` and is designed around an **Event Loop**.

* **Non-blocking I/O:** When an ASGI application hits an I/O operation (e.g., waiting for database results), it uses the `await` keyword to yield control back to the event loop.
* **Task Swapping:** Instead of sitting idle and blocking a thread, the event loop immediately switches to process other incoming requests or tasks.
* **Resuming:** Once the database operation finishes, the event loop is notified and resumes the original request right where it left off.

#### Real-world Analogy: The Restaurant
* **WSGI (Synchronous):** A waiter (thread) takes your order, goes to the kitchen, stands there waiting for the food to be cooked, serves you, and only then goes to take the next table's order. You need as many waiters as there are tables.
* **ASGI (Asynchronous):** A single waiter takes your order, sends it to the kitchen, and immediately goes to take orders from other tables. When your food is ready, they return to serve you. A single waiter can handle dozens of tables concurrently.

---

### 3. Why ASGI is ideal for "Lots of Concurrent I/O"

1. **WebSockets and Long Connections:**
   WebSockets require a connection to remain open indefinitely. In WSGI, keeping 1,000 WebSockets open would require 1,000 active threads, which would crash most standard servers due to memory exhaustion. ASGI handles thousands of idle, open connections on a single thread because they don't consume thread resources while waiting for data.
2. **Minimal Resource Overhead:**
   Because ASGI doesn't need to spawn a new OS-level thread for every connection, CPU context-switching overhead and memory footprint remain extremely low, even under heavy load.
3. **Optimized for Modern Web Applications:**
   Modern apps frequently communicate with microservices, external APIs, databases, caches (Redis), and message queues. Because almost all of these operations are I/O-bound rather than CPU-bound, ASGI maximizes the throughput of your server.


**Q2. FastAPI vs Flask vs Django — when would you pick FastAPI?**
"Flask is lightweight but synchronous and doesn't give you validation or docs out of the box. Django is batteries-included — great if you want an ORM, admin panel, the whole framework — but it's heavier than you need for a pure API service. FastAPI sits in the sweet spot for building fast, well-validated, well-documented APIs, especially when you want async. For this kind of backend-API role, FastAPI is the natural choice."

**Q3. What's the difference between an async and a sync endpoint in FastAPI?**
"If I declare an endpoint with `async def`, it runs on the event loop, and I should use it when I'm doing awaitable I/O — like an async database driver or an async HTTP client. If I declare it with regular `def`, FastAPI runs it in a threadpool so it doesn't block. The big mistake to avoid is putting blocking code — like the `requests` library or `time.sleep` — inside an `async def`, because that blocks the entire event loop and kills your concurrency. So: async endpoint plus async libraries, or sync endpoint for blocking work.

The production failure that catches people: you write `async def` but call `requests.get()` inside it. It works fine locally with 1 user. Under load with 50 concurrent users, it freezes the entire event loop for everyone. Every user waits. The fix: use `httpx.AsyncClient`, or switch to a sync endpoint so FastAPI runs it in a threadpool.

→ Follow-up: "What happens to other requests while a blocking call runs in an async endpoint?" — The entire event loop stalls. Every other request that's waiting on I/O is frozen until the blocking call returns."

**Q4. What is dependency injection in FastAPI / what is `Depends`?**
"`Depends` is FastAPI's dependency injection system. Instead of repeating logic in every endpoint, I write a function — say, one that gives me a database session, or one that extracts and validates the current user from a token — and I inject it into the endpoint with `Depends`. The benefits are reusability, cleaner code, and testability — in tests I can override a dependency with a fake one. A common pattern is a database-session dependency that uses `yield` to open the session before the request and close it after.

One gotcha in production: if you have a `yield`-based DB session dependency and the endpoint also fires a BackgroundTask, the session closes *before* the task runs — because session cleanup happens at response time, before background tasks execute. The fix: pass the data you need into the task, not the session itself."

**Q5. How do you validate incoming data?**
"With Pydantic models. I define a model with typed fields — and FastAPI automatically validates the incoming request body against it. If validation fails, it returns a 422 with a clear, field-level error, and I didn't have to write any of that. I can add constraints with `Field`, like minimum length or value ranges, and custom validators for more complex rules."

**Q6. How do you handle errors in FastAPI?**
"For expected errors I raise `HTTPException` with the right status code and a message — like a 404 if a resource isn't found. For consistency, I usually register custom exception handlers so every error comes back in the same shape — something like an `error` object with a code and a message — which makes life much easier for the frontend. And input validation errors are handled automatically by Pydantic as 422s."

**Q7. How do you handle authentication? (short version — full detail in Section 3)**
"Typically JWT-based. The user logs in, I issue a signed token, and the client sends it in the `Authorization: Bearer` header. I have a dependency that extracts the token, verifies the signature and expiry, and gives me the current user — and I inject that into any protected endpoint."

**Q8. How do you make a FastAPI service scale and perform well?**
"A few things. I run multiple worker processes — Uvicorn workers managed by Gunicorn — to use all the CPU cores. I keep the service stateless so I can scale horizontally behind a load balancer. I use connection pooling for the database and reuse my HTTP client. I cache hot reads in Redis. I paginate large responses. I use async for concurrent I/O, and I push slow or heavy work onto a background queue like Celery so the API stays responsive. And I put timeouts and retries on any outbound calls.

→ Follow-up: "What's the rule of thumb for worker count?" — Start with 2 × CPU cores + 1. Then measure — if workers are blocking on I/O more than CPU, you can add more. If they're CPU-saturated, more workers don't help."

**Q9. How would you structure a large FastAPI application?**
"I split it into layers. Routers grouped by domain using `APIRouter`, Pydantic schemas separate from the database models, a services layer for business logic, a database layer for sessions and migrations with Alembic, and a core module for config and security. Config comes from environment variables via pydantic-settings — never hardcoded. That separation keeps it testable and maintainable as it grows."

**Q10. BackgroundTasks vs Celery?**
"`BackgroundTasks` is FastAPI's built-in, lightweight way to run something after the response — like sending an email. It's in-process, so if the server restarts mid-task, it's lost. Celery is a proper distributed task queue with a broker like Redis or RabbitMQ — it's durable, retryable, and can be scheduled and scaled independently. So for fire-and-forget small stuff, BackgroundTasks; for important, long-running, or heavy jobs, Celery."

**Q11. What's CORS and why does it matter?**
"CORS is Cross-Origin Resource Sharing — it's the browser security mechanism that controls whether a frontend on one origin can call your API on another. Since the React or Next.js frontend usually runs on a different origin than the API, I have to add CORS middleware in FastAPI and allow the frontend's origin — otherwise the browser blocks the requests. It's a really common gotcha when wiring up a frontend."

**Q12. How do you test a FastAPI app?**
"I use pytest with FastAPI's TestClient, which lets me call endpoints in tests without running a real server. I override dependencies — like swapping the real database for a test one — and I mock external services. I aim for mostly fast unit tests, some integration tests, and a few end-to-end."

**Q13. What's a CORS misconfiguration that causes real production pain?**
"The one that bites almost every team: setting `allow_origins=['*']` with `allow_credentials=True`. That combination is invalid — browsers reject it because it would let any website make credentialed requests to your API. The fix is explicit origins. The second trap: forgetting to add `Authorization` to `allow_headers` — the preflight OPTIONS request succeeds, but the actual authenticated request fails silently. When the React team says 'auth calls are being blocked,' check those two things first."

# SECTION 2 — Python

⚠️ Weak answer trap: saying "the GIL prevents true parallelism" without explaining what that means in practice. The senior answer shows you know when it actually matters.

**Q13. What is the GIL?**
"The GIL — Global Interpreter Lock — is a lock in CPython that means only one thread can execute Python bytecode at a time. The practical consequence: threading doesn't give you true parallelism for CPU-heavy work. But threads *do* help for I/O-bound work, because a thread releases the GIL while it's waiting on I/O. So the rule is: for I/O-bound work, use threads or async; for CPU-bound work, use multiprocessing, which uses separate processes and sidesteps the GIL entirely.

The part that trips people up in interviews: async I/O doesn't fight the GIL at all. You're not threading — you're cooperatively yielding control at await points. GIL matters for CPU-bound threads, which you shouldn't be using anyway."

**Q14. Threading vs multiprocessing vs asyncio — when each?**
"All three are about doing more than one thing. Threading and asyncio are for I/O-bound work — lots of waiting on network or disk. Asyncio is single-threaded and very efficient at high concurrency because there's no thread overhead, but everything has to be non-blocking. Multiprocessing is for CPU-bound work — heavy computation — because it runs real parallel processes. Short version: I/O-bound goes to async or threads, CPU-bound goes to multiprocessing."

**Q15. What's a decorator?**
"A decorator is a function that wraps another function to add behavior without changing the original's code. You see them everywhere — logging, timing, caching with `lru_cache`, authentication checks, retries. Under the hood, `@decorator` on a function just means 'pass this function through the decorator and replace it with the result.'"

**Q16. What's a generator / `yield`?**
"A generator is a function that produces values lazily, one at a time, using `yield` instead of `return`. Instead of building a whole list in memory, it produces each item on demand. It's great for streaming large datasets — like processing a huge query result or a big file — without loading everything into memory at once. A real production example: streaming a 1-million-row database result. If you load it into a list first, you're holding 4GB in memory. With a generator, you hold one row at a time — memory stays flat regardless of table size. That's the pattern I used for large query result processing."

**Q17. What's a context manager / the `with` statement?**
"A context manager handles setup and cleanup automatically — the classic example is opening a file with `with open(...)`, which guarantees the file gets closed even if an error happens. You define it with `__enter__` and `__exit__`, or more simply with the `contextlib` decorator. I use them for anything that needs guaranteed cleanup — files, database sessions, locks."

**Q18. Mutable vs immutable types, and the mutable default argument trap?**
"Lists, dicts, and sets are mutable; strings, tuples, ints are immutable. The classic trap is writing a function with a default argument like `def f(x=[])` — that list is created once and shared across every call, so it accumulates state between calls, which is almost never what you want. The fix is to default to `None` and create a fresh list inside the function."

**Q19. `is` vs `==`?**
"`==` checks if two values are equal. `is` checks if they're literally the same object in memory — same identity. You use `==` for value comparison and `is` mainly for checking against `None`, like `if x is None`."

**Q20. How does Python manage memory / garbage collection?**
"Python primarily uses reference counting — every object tracks how many references point to it, and when that hits zero, it's freed. On top of that there's a cycle-detecting garbage collector for objects that reference each other in a loop, which reference counting alone can't clean up."

**Q21. What is Pydantic and why use it?**
"Pydantic is a data-validation library built on type hints. You declare a model with typed fields, and it validates and coerces incoming data, raising clear errors when something's wrong. It's the backbone of FastAPI — request and response models are Pydantic models. I also use it for settings management, loading config from environment variables in a typed, validated way."

**Q22. The mutable class attribute trap — have you seen it?**
"It's the same problem as mutable default arguments, but harder to spot. If you write `class Foo: items = []`, that list is shared across *all instances* of the class — it's a class attribute, not an instance attribute. Every instance you create appends to the same list. The fix: initialize it in `__init__`: `self.items = []`. I've seen this create genuinely confusing bugs where adding to one object mysteriously affects another."

# SECTION 3 — Authentication & API Design

⚠️ Weak answer trap: saying "JWT is secure because it's signed." Signing and encryption are different. A senior answer acknowledges what signing does NOT protect.

**Q22. Explain JWT.**
"A JWT — JSON Web Token — is a compact, signed token with three parts separated by dots: a header, a payload, and a signature. The header says which algorithm. The payload holds claims — like the user ID, an expiry time, and maybe their roles. The signature is created by signing the header and payload with a secret key. The whole flow: the user logs in, the server issues a JWT, the client sends it on every request in the `Authorization: Bearer` header, and the server verifies the signature and the expiry — no database lookup needed, which is what makes it scale well. One important point: a JWT is signed, not encrypted, so you never put secrets in the payload. And 'secrets' includes things you might not think of — like the user's email or roles. JWT is signed, not encrypted — anyone can base64-decode the payload and read it in browser DevTools. We had a developer put the user's email and role in the token 'for convenience' and it was visible in the Network tab to anyone who knew to look.

→ Follow-up: "How do you revoke a JWT before it expires?" — Short expiry (15-30 minutes) is the first line. For explicit revocation — logout, compromised account — store the token's unique 'jti' claim in a Redis blacklist and check it on each request. It adds one Redis lookup per request, which is acceptable."

**Q23. JWT vs session-based authentication?**
"With sessions, the server stores session state and the client holds a session ID — which means the server has to look it up, and you need shared session storage to scale. JWTs are stateless — the token itself carries the identity and is verified by signature, so any server instance can handle any request without shared state. The trade-off is that JWTs are harder to revoke before they expire, so you keep them short-lived and use refresh tokens."

**Q24. Access token vs refresh token?**
"The access token is short-lived — say 15 minutes — and it's what you send with each request. The refresh token is long-lived and stored more securely; when the access token expires, the client uses the refresh token to get a new one without making the user log in again. This limits the damage if an access token leaks, while keeping the user logged in."

**Q25. Authentication vs authorization?**
"Authentication is *who you are* — proving your identity, like logging in. Authorization is *what you're allowed to do* — your permissions. A real example from my work: I implemented attribute-level RBAC — role-based access control — where permissions were defined down to individual attributes, not just broad roles. That's authorization."

**Q26. What is OAuth2? What's OIDC?**
"OAuth2 is a framework for delegated authorization — it lets one app access resources on behalf of a user without the user sharing their password. The classic example is 'Log in with Google.' There are a few players: the user, the client app, the authorization server like Google, and the resource server. The most common flow for web apps is the authorization code flow — the user is redirected to the auth server, consents, you get a code, and you exchange that code for an access token. OIDC — OpenID Connect — is a thin identity layer built on top of OAuth2; it adds an ID token that tells you who the user actually is. So OAuth2 handles authorization, and OIDC adds authentication."

**Q27. How do you secure an API?**
"Several layers. HTTPS everywhere. Validate and sanitize all input with Pydantic. Use parameterized queries so there's no SQL injection. Authenticate every protected endpoint and check authorization per resource. Rate-limit to prevent abuse. Lock down CORS to known origins. Never leak internal details or stack traces in error responses — log them internally, return a generic message. Keep secrets in environment variables or a secret manager, and follow least privilege for any credentials.

The #1 API security mistake I've seen in the wild: broken object-level authorization. The team authenticates correctly — valid JWT, user is real — but forgets to verify the user actually *owns* the resource they're requesting. `GET /ads/{id}` verifies the token but not whether that ad belongs to this user. Any authenticated user can access any other user's data. OWASP (Open Web Application Security Project) calls this the top API vulnerability."

**Q28. What are the main HTTP methods and status codes?**
"GET reads data, POST creates, PUT replaces, PATCH partially updates, DELETE removes. For status codes: 200 is OK, 201 created, 204 no content; 400 is a bad request, 401 unauthenticated, 403 forbidden, 404 not found, 409 conflict, 422 validation error; and 500 is a server error. GET, PUT, and DELETE are idempotent — doing them twice has the same effect as once — while POST isn't."

**Q29. How do you design a good REST API for a frontend team?**
"I keep resources as plural nouns — like `/ads` and `/ads/{id}` — and use the HTTP methods properly. I keep responses consistent, including a consistent error shape so the frontend can handle errors uniformly. I add pagination for large lists, filtering and sorting via query params, and I version the API with a `/v1` prefix so I never break existing consumers. And because FastAPI auto-generates OpenAPI docs, the frontend always has a live contract to build against."

**Q30. How do you handle a slow or flaky third-party API?**
"I always set a timeout so a slow dependency can't hang my service. I add retries with exponential backoff for transient failures. For a dependency that's repeatedly failing, a circuit breaker stops hammering it and lets it recover. Where it makes sense, I cache responses, and I design fallbacks so a failure degrades gracefully instead of taking everything down. I actually did exactly this in a project — when an AI model API could fail, I built a regex fallback so the tool stayed up 100% of the time."

# SECTION 4 — Databases & SQL (theory; queries in SQL_WITH_SOLUTIONS.md)

**Q31. Explain the different JOINs.**
"An INNER JOIN returns only the rows that match in both tables. A LEFT JOIN returns all rows from the left table plus matching rows from the right, with NULLs where there's no match — handy for 'find records with no related record' by checking for NULL. A RIGHT JOIN is the mirror image. A FULL OUTER JOIN returns everything from both sides. And a self-join is a table joined to itself, like matching employees to their managers in the same table."

**Q32. WHERE vs HAVING?**
"WHERE filters individual rows *before* grouping. HAVING filters *after* grouping, so it works on aggregated results. For example, WHERE status equals 'paid' filters rows, but HAVING SUM(amount) greater than 1000 filters the grouped totals. The reason they're different comes down to the order SQL executes things — filtering happens before grouping, then HAVING applies to the groups."

⚠️ Weak answer trap: "indexes make queries faster." Every candidate says this. The senior answer covers: the write penalty, composite index column order, when NOT to index, and how to verify an index is being used.

**Q33. What's an index and what's the trade-off?**
"An index is a data structure — usually a B-tree — that lets the database find rows quickly without scanning the whole table, so it speeds up lookups, joins, and sorts on the indexed columns. The trade-off is that every index slows down writes, because the index has to be updated too, and it uses extra storage. So I index columns I frequently filter, join, or sort on — but I don't over-index. To check whether a query is using an index, I run EXPLAIN ANALYZE.

→ Follow-up: "How do you actually read EXPLAIN ANALYZE output?" — Look for 'Seq Scan' on a large table — that's the red flag meaning no index is being used. 'Index Scan' means it's working. Also check actual rows vs estimated rows — a big discrepancy means stale table statistics; run ANALYZE to update them."

**Q34. How would you debug a slow query?**
"First I'd run EXPLAIN ANALYZE to see the query plan — is it doing a full table scan where it should be using an index? Then I'd check for missing indexes on the filtered or joined columns. I'd look for the N+1 problem — where code runs one query per row instead of a single join. And I'd consider rewriting the query, adding the right index, or caching the result if it's read-heavy.

A real one from production: a date filter written as `WHERE DATE(created_at) = '2026-01-01'` looks correct but wraps the column in a function, which prevents the B-tree index from being used. EXPLAIN ANALYZE shows a full seq scan. The fix: `WHERE created_at >= '2026-01-01' AND created_at < '2026-01-02'` — the index kicks in and the query goes from seconds to milliseconds."

**Q35. What is the N+1 query problem?**
"It's when you fetch a list with one query, then run an additional query for each item to get related data — so for N items you run N+1 queries, which is really slow. The fix is to fetch the related data up front with a JOIN or eager loading, so it's one or two queries total instead of hundreds."

**Q36. Explain ACID.**
"ACID describes the guarantees of a reliable transaction. Atomicity — all the operations in a transaction happen, or none do. Consistency — the database moves from one valid state to another, respecting constraints. Isolation — concurrent transactions don't corrupt each other. And Durability — once committed, the data survives even a crash."

**Q37. What is database normalization?**
"Normalization is organizing tables to reduce redundancy and keep data consistency — roughly, each fact is stored once. The first few normal forms remove repeating groups and dependencies that don't belong. The trade-off is that highly normalized data needs more joins to read, so sometimes you deliberately denormalize — duplicate some data — to speed up reads, accepting the redundancy. It's a read-performance versus consistency trade-off."

**Q38. How do you model a many-to-many relationship?**
"With a junction table — also called a bridge table — that sits between the two tables and holds foreign keys to both. For example, if agents can belong to many groups and groups have many agents, you make a third table with an agent ID and a group ID per row. I've done exactly this — I built multi-agent junction tables in a PostgreSQL schema."

**Q39. How do you prevent SQL injection?**
"Always use parameterized queries — where the values are passed separately from the SQL text — or use an ORM that does this for you. Never build SQL by concatenating user input into the string. That way user input is treated as data, never as executable SQL."

**Q40. PostgreSQL vs MySQL vs SQL Server — your experience?**
"They're all relational, ACID-compliant SQL databases, and the core skills transfer directly between them. My deepest hands-on experience is with PostgreSQL — I've done schema design, complex queries, and worked with it through SQLAlchemy. PostgreSQL is known for being very feature-rich — things like JSONB and strong standards compliance. The fundamentals — joins, indexing, transactions — apply the same way across MySQL and SQL Server, with minor syntax differences."

# SECTION 5 — Snowflake (basic — keep it short and confident)

**Q41. What is Snowflake and how is it different from PostgreSQL?**
"Snowflake is a cloud-native data warehouse — it's built for analytics, running big aggregations over large volumes of data, whereas PostgreSQL is a transactional database built for an application's day-to-day reads and writes. So it's OLAP versus OLTP. Snowflake is fully managed — you don't run servers — it stores data in a columnar format, and it scales compute on demand. And importantly, you query it with standard SQL, so my SQL skills carry straight over."

**Q42. What's special about Snowflake's architecture?**
"The headline feature is that it separates storage from compute. Your data lives in one storage layer, and compute happens in independent clusters called virtual warehouses. That means you can spin compute up for a heavy job and back down when idle, and multiple teams can query the same data without competing for resources. You pay for compute only when you use it."

**Q43. What's a virtual warehouse?**
"It's a compute cluster in Snowflake — it's what actually runs your queries. They come in sizes you can scale up or down, and they can auto-suspend when idle and auto-resume when a query comes in, which keeps costs down."

**Q44. How would a Python backend integrate with Snowflake?**
"There's an official Python connector — `snowflake-connector-python` — and there's also a SQLAlchemy dialect. So from a FastAPI backend, I'd connect, run standard SQL, and map the results into Pydantic models to serve over the API — and cache hot reads in Redis. I'd treat it like any other SQL data source behind a clean data-access layer. Honestly, since it's standard SQL with a Python connector, integrating it is straightforward."

# SECTION 6 — System Design & Microservices

**Q45. Monolith vs microservices — when do you use each?**
"A monolith is a single deployable application — it's simpler to build, test, and debug, and transactions are easy because everything's in one place. Microservices split the system into small, independently deployable services, each owning its data — which lets teams and services scale independently, at the cost of a lot more complexity: network calls, distributed data, harder debugging. My honest take is start with a monolith, or a well-organized modular monolith, and only split into services when team size or scaling needs actually justify it. Don't reach for microservices prematurely.

The real cost nobody talks about in interviews: distributed transactions, cross-service debugging, data consistency across service boundaries. I've seen teams go microservices-first and spend six months building infrastructure — service mesh, distributed tracing, secrets management — instead of building the product. Split when you have a concrete reason: different scaling requirements, different deployment cadence, different team ownership."

**Q46. How do services communicate in a microservices setup?**
"Two main styles. Synchronous — REST over HTTP, or gRPC for internal service-to-service calls. And asynchronous — through a message queue like RabbitMQ, Redis, or Kafka, where services communicate via events. Sync is simple and direct; async decouples services, absorbs traffic spikes, and lets you retry failed work. I've used gRPC for an internal model gateway because it's fast, strongly typed, and runs over HTTP/2."

**Q47. REST vs gRPC?**
"REST uses JSON over HTTP — it's human-readable, universal, and works great for public and browser-facing APIs. gRPC uses binary protobuf over HTTP/2 — it's faster, strongly typed via a schema, and supports streaming, which makes it ideal for internal service-to-service communication. So REST for public-facing, gRPC for high-performance internal calls."

**Q48. How do you handle a long-running task in an API?**
"You don't make the user wait for it. I accept the request, validate it, and put the work onto a background queue like Celery, then immediately return a response — usually a job ID. The client can poll a status endpoint or get notified by a webhook when it's done. That keeps the API fast and responsive, and lets me scale the workers separately. I've built exactly this pattern for slow processing work."

**Q49. How do you scale a backend service?**
"The main lever is horizontal scaling — running more instances behind a load balancer — which works as long as the service is stateless, so any instance can handle any request. On top of that: cache hot data in Redis, scale the database with read replicas and connection pooling, use message queues to smooth out spikes, and partition or shard data if it gets huge. Statelessness is the key enabler — that's why JWT auth and not storing local session state matter."

**Q50. How do you make a system resilient?**
"Assume things will fail. Timeouts on every external call so nothing hangs. Retries with backoff for transient failures. Circuit breakers to stop calling a dependency that's down. Graceful degradation and fallbacks so a partial failure doesn't take the whole system down. Health checks, idempotency so retries are safe, and good observability — structured logs with request IDs, metrics, and alerting — so I can actually see what's happening in production."

**Q51. Walk me through designing the backend for an ad-creative generation API.** *(your client's domain)*
"I'd start by clarifying requirements — expected load, how long generation takes, consistency needs. Since generation is slow, I'd make it asynchronous: a `POST /generations` endpoint validates the request with Pydantic, enqueues a job on Celery, and returns a job ID immediately. A worker picks it up, calls the AI generation service, and stores the result — say the asset in object storage like S3, and metadata in PostgreSQL. The client polls a `GET /generations/{id}` endpoint or gets a webhook. I'd add JWT auth with RBAC, rate-limit the expensive generation endpoint, cache hot reads in Redis, paginate listings, and wire up logging and metrics throughout. The key design decision is the async job queue — it keeps the API responsive even though the underlying work is slow. This is actually very close to systems I've built.

→ Follow-up: "What happens if the AI generation service goes down?" — Circuit breaker stops sending requests after N consecutive failures. Jobs in the queue get a 'pending/degraded' status. When the service recovers, the circuit resets and workers retry queued jobs. The user gets their result late — degraded experience, not a broken one."

**Q52. What is caching and how do you keep a cache fresh?**
"Caching stores the result of expensive operations so you don't redo them. The common pattern is cache-aside: check the cache first; on a miss, hit the database and then populate the cache, with a TTL — a time-to-live — so entries expire. The hard part is invalidation — when the underlying data changes, you either let the TTL expire it or explicitly evict it. I've used Redis caching to turn repeated lookups from a slow operation into near-instant ones."

# SECTION 7 — DevOps, CI/CD & Git

**Q53. What's the difference between merge and rebase?**
"Both integrate changes from one branch into another. Merge creates a merge commit and preserves the full history as it happened. Rebase replays your commits on top of another branch to create a clean, linear history. The golden rule is don't rebase a branch that others are already working on or that's been pushed and shared, because it rewrites history. I use merge for shared branches and rebase to tidy up my own local work before opening a PR."

**Q54. Walk me through your Git workflow.**
"I create a feature branch off the main branch, commit small, focused changes with clear messages, and push. Then I open a pull request, where CI automatically runs linting and tests, and a teammate reviews it. We discuss, I address feedback, and once it's approved and CI is green, it gets merged. I actually authored code-review checklists at one job — covering things like thread safety and Docker best practices — that the team adopted as a standard."

**Q55. What is CI/CD?**
"CI — continuous integration — means every time someone pushes code, an automated pipeline runs the linters and tests and builds the project, so problems are caught early. CD — continuous delivery or deployment — extends that to automatically packaging and deploying the code once it passes. A typical pipeline checks out the code, installs dependencies, runs the linter and tests, builds a Docker image, pushes it to a registry, and deploys it."

**Q56. How do you deploy without downtime?**
"There are a few strategies. Rolling deployment updates instances gradually. Blue-green keeps two environments and switches traffic over once the new one is verified. Canary releases the change to a small percentage of traffic first, watches it, then rolls out fully. They all aim to release safely with no downtime and an easy rollback."

**Q57. Dockerfile best practices?**
"Use a small base image like a slim variant, run as a non-root user, order layers so dependencies are cached separately from your code, use a `.dockerignore`, pin your versions, and never bake secrets into the image. Multi-stage builds help keep the final image small. I actually wrote Docker best-practice checklists that my team adopted.

⚠️ The Docker mistake that trips up AI-assisted developers: using `FROM python:latest` as the base image. The `latest` tag is mutable — a new Python version ships, your image changes silently, and something breaks in production. Pin it: `FROM python:3.11-slim`. Second trap: passing secrets as `ENV` in a Dockerfile — they're visible in `docker history` to anyone with image access. Inject secrets at runtime via environment variables, not at build time."

**Q58. How do you monitor and log a production API?**
"Structured logging — JSON logs with a request ID so I can trace a single request across services — sent to a central system. Metrics — request rate, error rate, and latency percentiles like p95 and p99 — usually with something like Prometheus and Grafana. Health-check endpoints for liveness and readiness. And alerting on thresholds so the team gets paged when error rates or latency spike. One important rule: never log secrets, tokens, or personal data."

**Q59. How do you debug a production incident?**
"I start with the data — check the logs and metrics to see what changed and when: did errors spike after a deploy? I use the request ID to trace a failing request end to end. I try to reproduce it, form a hypothesis about the cause, and verify it before changing anything — rather than guessing and randomly trying fixes. Once I understand it, I fix it, and ideally add a test or alert so it can't silently happen again.

The order matters more than people realize. Check metrics first to see *when* the error rate spiked — was it after a deploy? Correlated with a traffic increase? That tells you *what kind* of problem you're dealing with before you touch any code. Then logs with a failing request ID. Form a hypothesis before you change anything."

**Q60. Describe your Agile process.**
"I've worked in Scrum — work organized into sprints, with daily standups, sprint planning at the start, a review or demo at the end, and a retro to improve. Work is tracked as stories in a tool like JIRA. I've delivered Agile sprint reports and kept to strict deployment schedules with zero missed deliveries."
