# PROJECT 1 — 5G Failure Remediation Pipeline (your strongest "impact" story)

### The 90-second story
"Picture a 5G core test lab. Every time something failed — an authentication timeout, a dropped handover, congestion — an engineer had to scroll through gigabytes of packet-capture files by hand to find the cause. It took hours. And the frustrating part was that the same failures kept recurring, and we kept diagnosing them from scratch.

So I built a pipeline that does it automatically. It reads the packet captures using Pyshark, identifies the signaling error, and proposes a fix.

The key decision was *how* it recognizes errors. Keyword rules are brittle — the same fault shows up with slightly different wording each time. So instead, I embedded known error patterns into a vector database and matched failures *semantically* — so it recognizes the fault even when it's phrased differently. Then an LLM, grounded on the retrieved context, writes a contextual fix suggestion. And because certain errors recurred constantly, I cached them in Redis so a repeat failure resolved almost instantly.

The result: log analysis went from hours to seconds — roughly 70% of routine errors auto-resolved, and mean-time-to-resolution dropped about 55%.

What I'm proud of is the mindset — I treated an unpredictable AI model like any other flaky dependency, with grounding, caching, and fallbacks. That's really backend reliability thinking."

### The "why" follow-ups
- **Why a vector database instead of keyword/rule matching?** "Because the same error appears with different wording every time, so exact rules are brittle and miss things. Semantic matching against known patterns catches the fault regardless of phrasing. The trade-off is you need an embedding step and a vector store to maintain, but the improvement in recall was the whole point."
- **Why an LLM for the fix instead of a fixed lookup table?** "Because the right fix depends on the specific context of the failure, not just its type. A static table gives one canned answer; the LLM composes something contextual. And it's grounded on the retrieved known-patterns, so it's not just freely guessing."
- **Why Redis for caching?** "The same routine errors recurred constantly, so caching the lookups turned repeated work into instant responses and reduced load on the retrieval path. I used a TTL to handle staleness. An in-memory dict wouldn't survive restarts or be shared across processes — Redis solved both."
- **Why Pyshark?** "It's a Python wrapper over tshark, so I could parse the 5G signaling packets programmatically inside the pipeline, using tshark's strong protocol dissectors, rather than shelling out and parsing raw text."
- **How did you measure 70% / 55%?** "Against the prior manual triage baseline over a sample period — it's an observed/estimated improvement, not a formal benchmark, but it was a dramatic and consistent reduction."

# PROJECT 2 — NFTRACE (your strongest "architecture" story)

### The 90-second story
"Our CI/CD (Continuous Integration/Continuous Deployment) pipelines for testing network functions were slow and fragile. The biggest issue was that the test scenarios were tangled up with the validation logic — so changing how we validated something risked breaking the test scenarios themselves, and parallel test runs would step on each other's state.

So I architected NFTRACE — a distributed tracing platform that cleanly separates *what* you're testing from *how* you validate it.

Two decisions made it work. First, I exposed FastAPI lifecycle endpoints — start, stop, merge, validate — so test scenarios became composable building blocks instead of one big tangle. Second, the hard part was running tests in parallel without them corrupting each other's state. I used Redis-backed session caching to give each run an isolated session, and SQLite to persist node state and execution history. An in-process store couldn't share state safely across parallel workers, and a full database server would've been overkill for that scope — Redis hit exactly the right balance. I also used XML-RPC for the client-side SDK to fit the existing tooling.

The result was a 50% reduction in pipeline validation time across our CI/CD workflows.

It's the project I'm proudest of architecturally, because the win came from a design decision — decoupling — not just from writing code."

### The "why" follow-ups
- **Why decouple scenarios from validation?** "Maintainability and reuse. When they were coupled, every validation change was high-risk and could break unrelated scenarios. Decoupling let each evolve independently and made the whole thing safer to change — that's where the 50% time saving came from."
- **Why Redis for sessions instead of in-process memory?** "Because tests ran in parallel across workers and each needed an isolated, shareable session. An in-process dictionary can't be shared safely across separate worker processes. Redis gave fast, shared, isolated session storage. The trade-off is an extra dependency to run, which was well worth it."
- **Why SQLite instead of PostgreSQL?** "The persisted data — node state and execution history — was local and modest in volume. SQLite is embedded and zero-config, perfect for that. Running a full PostgreSQL server would've added operational overhead with no real benefit at that scope. If write concurrency had grown, I'd revisit that."
- **Why XML-RPC for the SDK?** "It was a simple, built-in cross-language RPC (Remote Procedure Call) that fit the existing client ecosystem. Honestly, if I built it today I might choose gRPC (Google Remote Procedure Call — binary, HTTP/2, strongly typed) for the stronger typing — but XML-RPC matched the constraints at the time."

### 💀 DANGER ZONE — NFTRACE

**💀 "What was the exact Redis key schema for session isolation?"**
→ Honest answer: "The key was `session:{uuid}` where the UUID was generated fresh for each test run. The value was a JSON blob holding the scenario's execution state — which nodes had run, their outputs, current status flags. Each parallel worker only read and wrote its own key, so runs couldn't corrupt each other."
→ Don't say: A different structure if you're not sure — this specific detail is defensible and accurate.

**💀 "What happened if Redis was unavailable mid-run?"**
→ Honest answer: "That's a fair gap to call out. If Redis went down mid-run, parallel test isolation would break — workers would fail to read or write their session state, causing test failures. We had a health check on startup but not a graceful fallback path. If I rebuilt it today, I'd add a `/health` endpoint that checked Redis connectivity before accepting test runs."
→ Don't say: "We had full fault tolerance" — be honest about the gap and what you'd fix.

**💀 "Why XML-RPC specifically — why not REST for the client SDK?"**
→ Honest answer: "It matched the existing client tooling ecosystem — the consumers already had XML-RPC clients and changing that would've required coordinating changes on the client side. Today I'd choose gRPC for the strong typing and better performance — that's actually what I used at Brane for the model gateway. XML-RPC was a pragmatic fit-to-existing-constraints decision."

# PROJECT 3 — Brane AI Agent Runtime (your "depth + RBAC + microservices" story)

### The 90-second story
"At Brane I worked on the runtime that actually *runs* AI agents inside a no-code platform — the engine that decides what an agent can see, do, and remember. I was there a focused couple of months and worked across three areas: the PostgreSQL schema, the model gateway, and the agent loop.

On the data side, I implemented schema components including *attribute-level* RBAC — permissions defined down to individual attributes, not just broad roles — using junction tables for the many-to-many relationships between agents and logical objects. And because those permission checks sat on a hot path, I added caching for them.

On the serving side, I integrated the LLM inferencing layer through a gRPC model gateway that routed across multiple model types — instruct, thinking, vision — and was fully stateless, so it scaled horizontally.

And because LLM outputs are sometimes malformed, I hardened the response parser and helped build a verifier-with-retry loop that feeds errors back for correction.

The result was a runtime that handled multi-agent execution reliably, with reduced permission-check and tool-invocation overhead. Across all of it, my instinct was the backend one — treat the unreliable parts, permissions and model outputs, with caching, validation, and retries."

### The "why" follow-ups
- **Why gRPC for the model gateway instead of REST?** "It was internal service-to-service communication at volume. gRPC runs over HTTP/2 with binary protobuf, so it's faster and smaller than JSON, it's strongly typed via a schema, and it supports streaming. REST would've been the choice for a public or browser-facing API, but for internal model serving, gRPC's performance and type-safety won."
- **Why stateless for the gateway?** "Inference routing doesn't need per-request server state, so keeping it stateless means any instance can handle any request and I scale just by adding instances. The shared state — like caches — lives in Redis or the database instead."
- **Why PostgreSQL, not a NoSQL store?** "The data was highly relational — agent identities, many-to-many links, permission rows — and needed referential integrity and ACID guarantees. JSONB covered the flexible parts. NoSQL would've sacrificed the integrity and joins we depended on."
- **Why attribute-level RBAC instead of simple roles?** "The requirement was fine-grained control — permissions per attribute, not just per role. Role-level would've been too coarse. The cost is more permission rows and more checks, which is exactly why I added the caching."
- **Why cache permission checks?** "They happened repeatedly on a hot path for the same subjects, so caching cut redundant database lookups and latency. The trade-off is invalidating the cache when permissions change."
- **What exactly was your contribution vs the team's?** *(Answer honestly and specifically)* "I worked on specific schema components — the identity tables, the junction tables, the RBAC rows, the execution sibling tables — the prompt assembly for the agent loop, and performance work like the RBAC caching and parser hardening. I was contributing within a larger runtime team, focused on those areas."

The junction tables handled the many-to-many relationships between agents and logical objects — one agent could be linked to multiple LOs and vice versa."

# How to rehearse (do this Saturday)
For each project:
1. Read the story once.
2. Close the file and tell it out loud — **time it, aim under 90 seconds.**
3. Then have someone (or Claude in a mock) fire the "why" questions — answer in the 4-beat pattern.
4. Record yourself once and listen for filler words, rushing the metric, or jargon you didn't explain.

When you can tell all three stories smoothly *and* defend every decision, you're ready. That combination — a clear story plus a solid "why" — is exactly what makes a senior engineer believable.

## What I'd Do Differently (senior signal — shows growth and honesty)

Prepare one honest answer per project. "What I'd change" answers are gold — they show you learned from the experience.

**5G Pipeline:**
"I'd add a more aggressive caching strategy for 'no known fix' results — right now a novel error that has no match goes through the full retrieval + LLM path every time. I'd cache the miss too, with a shorter TTL. And I'd add a queue depth metric with an alert — so we'd know the pipeline was backing up before users noticed slow resolution times."

**NFTRACE:**
"I'd add a `/health` endpoint that actively checked Redis connectivity before accepting test runs — we had no way to detect a silent Redis failure until test isolation broke. And if write volume grew significantly, I'd evaluate replacing SQLite with PostgreSQL for the persistence layer, since SQLite's write concurrency has limits."

**Brane:**
"I'd build the RBAC cache invalidation more defensively. Right now it invalidates on explicit permission change events, but if an event was missed for any reason, we'd serve stale permissions until the TTL expired. I'd add a shorter TTL as a safety net — maybe 60 seconds — so even in the worst case, stale permissions don't persist long."
